## 0. What M0 does

M0 is the milestone with **no model in it**. It builds the three things
every later model is judged by:

| Part | What it makes | Status |
|---|---|---|
| **A. ExpDate** | The public training data: downloaded, checked, looked at, measured, converted to YOLO format | done (13 Oct) |
| **B. Store test set** | The 99 store photos labelled with the expiry, tight date boxes and a failure tag, then frozen | done (21 Oct) |
| **C. Baselines** | The scores of two readers that already exist: RapidOCR + a regex (A), and Scanify (B) | A done (21 Oct); B to do |

**Done when** `results/m0_baselines.md` holds the baseline table on the
ExpDate test split and on the store photos, broken down by failure tag.

**Why it comes first.** A model is only as good as the data it learns
from and the test that judges it. If either is wrong, every later number
is wrong, and nothing crashes to tell you.

```
Part A: ExpDate (public, for training)
  download ──► check ──► look ──► measure ──► convert to YOLO ──► M1 trains on it
  (SHA-256)    (counts)   (contact   (box sizes)  (label files,
                           sheets)                 validation split)

Part B: store photos (private, for testing only)
  label by hand ──► import and check ──► freeze ──► every model is tested on it

Part C: baselines
  RapidOCR + regex  (A) ─┐
                         ├──► right / wrong / none per photo ──► results/m0_baselines.md
  Scanify's reader  (B) ─┘
```

### Two jobs: finding and reading

Reading an expiry date from a photo is really two jobs:

1. **Finding** (*detection*): *where* in the photo is the date? The answer
   is a box. M1 trains a model for this.
2. **Reading** (*recognition*): *what* does the text inside the box say?
   The answer is `2027-08-15`. M3 trains a model for this.

```
   the photo                    job 1: find                 job 2: read
 ┌────────────────────┐       ┌────────────────────┐
 │  NUTRI DOG FOOD    │       │  NUTRI DOG FOOD    │
 │                    │  ──►  │      ┌──────────┐  │  ──►   2027-08-15
 │  EXP: 15/08/2027   │       │  EXP:│15/08/2027│  │
 └────────────────────┘       └────────────────────┘
```

M0 prepares the data for both, and the baselines measure both together.

## 1. Images: computer vision basics

### 1.1 ★ An image is a grid of numbers

To a computer, a colour photo is a block of numbers with three sides:

- **height** rows,
- **width** columns,
- **3 channels**: how much red, green and blue each pixel has.

Each number goes from 0 (none) to 255 (full). They're stored as `uint8`,
a whole number that fits in 8 bits, which is why the top is 255.

```
one pixel = 3 numbers            the whole photo = height × width × 3
   R    G    B                   test_00001.jpg  = 1092 × 1455 × 3
 [192  151  129]  a light brown                  = 4,766,580 numbers
```

Black is `[0, 0, 0]`, white is `[255, 255, 255]`, pure red is
`[255, 0, 0]`. A greyscale image has 1 channel instead of 3.

**Where your CNN revision fits in.** The first convolution layer of a CNN
slides its filters over exactly this block. Each filter is 3 × 3 × 3: 3
pixels wide, 3 tall, and one slice per colour channel. The model never
sees a "photo", only these numbers. Before they go in, they're usually
divided by 255 so they run from 0 to 1. Ultralytics does that for us in
M1, so M0 never has to.

**In our code.** We open photos with Pillow (the `PIL` library), which
gives an `Image` object. `np.asarray(image)` turns it into the block of
numbers. [`load_upright()` ends with `.convert("RGB")`](../../src/bestbefore/images.py#L20),
so every photo comes out with exactly 3 channels. Without it, a greyscale
photo would have 1 channel and a PNG with transparency would have 4
(RGBA), and a model built for 3 would crash or read them wrong.

> **Try it**
>
> ```python
> import numpy as np
> from bestbefore.sets import load_set
> from bestbefore.images import load_upright
>
> s = load_set("real-test")[0]      # test_00001.jpg
> im = load_upright(s.image)        # a PIL image
> a = np.asarray(im)                # the same image, as numbers
> print(im.size)                    # (1455, 1092)
> print(a.shape, a.dtype)           # (1092, 1455, 3) uint8
> print(a[0, 0])                    # [192 151 129]: the top-left pixel
> ```
>
> Notice that `im.size` and `a.shape` list the two sides in **opposite
> orders**. That's the next section.

### 1.2 ★ Coordinates, and the (row, column) trap

Pixel positions start at `(0, 0)` in the **top-left** corner. `x` grows to
the right and `y` grows **downwards**, the opposite of a graph in maths
class.

```
 (0,0) ──────► x
   │
   │      (x1,y1) ┌──────────┐
   ▼              │2021.08.03│
   y              └──────────┘ (x2,y2)
```

**The trap.** Two libraries use two different orders:

| | Order | For test_00001 |
|---|---|---|
| Pillow, `im.size` | (width, height) | `(1455, 1092)` |
| numpy, `a.shape` | (height, width, channels) | `(1092, 1455, 3)` |
| numpy, one pixel | `a[y, x]`: row first | `a[0, 0]` |

numpy puts the row first because it treats the image as a list of rows:
first pick a row (`y`), then a pixel within it (`x`). Mixing the orders up
crops the wrong area, or crashes only on photos that aren't square. A
square test image hides the bug completely, so always test with a
rectangular one.

**In our code.** [`Sample` stores `width` and `height` as two named
fields](../../src/bestbefore/samples.py#L51-L52), so no code has to
remember an order. When boxes are drawn, `x` is always multiplied by the
width and `y` by the height:
[`contact_sheet.py` lines 46–47](../../scripts/contact_sheet.py#L46-L47).

> **Try it** (continues from 1.1): cut the date out of the photo with
> numpy.
>
> ```python
> from PIL import Image
>
> box = [b for b in s.boxes if b.label == "exp"][0]
> x1, y1, x2, y2 = box.xyxy                        # fractions, 0 to 1
> X1, X2 = round(x1 * s.width), round(x2 * s.width)
> Y1, Y2 = round(y1 * s.height), round(y2 * s.height)
> print(X1, Y1, X2, Y2)                            # 638 576 950 623
> crop = a[Y1:Y2, X1:X2]                           # rows (y) first!
> print(crop.shape)                                # (47, 312, 3)
> Image.fromarray(crop).save("data/date_crop.png") # open it and look
> ```
>
> Now swap the order to `a[X1:X2, Y1:Y2]` and print the shape. That's
> the bug, and Python gives no error.

### 1.3 ★ EXIF: phone photos are often stored sideways

A phone's camera sensor always captures in one direction. When you hold
the phone upright, it often **doesn't** rotate the pixels. It saves them
sideways and adds a small note inside the file: "turn me 90° when you
show me". That note is part of the **EXIF** data (extra information stored
in a photo, like the date it was taken and the camera model).

Photo apps read the note, so you never notice. Code that ignores it sees
the photo on its side. A box drawn on the upright view then lands in the
wrong place, **with no error message**.

The note is a number from 1 to 8:

| Flag | Meaning |
|---|---|
| 1 | already upright (also used when there's no note) |
| 3 | turn 180° |
| 6 | turn 90° clockwise |
| 8 | turn 90° anticlockwise |
| 2, 4, 5, 7 | mirrored versions (rare) |

Flags 5 to 8 swap width and height.

**In our code**, three small functions in
[`images.py`](../../src/bestbefore/images.py):

- [Lines 13–14](../../src/bestbefore/images.py#L13-L14): `0x0112` is the
  EXIF tag number for orientation (fixed by the EXIF standard), and
  `SIDEWAYS` lists the flags that swap the sides.
- [`load_upright()`, lines 17–20](../../src/bestbefore/images.py#L17-L20):
  `ImageOps.exif_transpose` turns the pixels the way the note says and
  then deletes the note, so the turn can't be applied twice.
- [`upright_size()`, lines 29–34](../../src/bestbefore/images.py#L29-L34):
  reads the size *without* decoding the pixels, which is much faster, and
  swaps the sides for flags 5 to 8.
  [`check_expdate.py` uses it](../../scripts/check_expdate.py#L23-L24) to
  compare every photo with the size in the JSON. A mismatch would mean
  the labels were drawn on the sideways view.
- [`tests/test_images.py`, lines 23–32](../../tests/test_images.py#L23-L32):
  makes a 40 × 20 test image with a red top-left corner and flag 6, then
  checks it opens as 20 × 40 with the red corner now at the top right.

**What we found.** Three ExpDate test photos carry a flag, and their JSON
sizes match the upright view, so their boxes were drawn upright. The
store photos come from phones, and **46 of the 99** carry a flag. Check 5
in B2 compared the size Label Studio drew on with `upright_size()` for
every photo: all matched, so every box was drawn on the upright view
(§4.4).

**The design lesson: one door.** Every script opens photos through
`load_upright`. If each script opened photos its own way, one day two of
them would disagree, and nothing would warn you.

> **Try it**: run the test, then read it.
>
> ```bash
> pytest tests/test_images.py -v
> ```

### 1.4 ★ Resizing, and why small dates are hard for a CNN

**The simple part.** YOLO resizes every photo so its long side is 640 px
(the *input size*). It keeps the shape and fills the leftover space with
grey; that's called **letterboxing**. Everything shrinks by the same
factor:

```
scale = 640 / long side of the photo
test_00001: 640 / 1455 = 0.44, so its 312 × 47 px date becomes 137 × 21 px
```

**The deep part, where your CNN revision comes in.** A CNN shrinks the
image as it goes deeper. Each layer with stride 2 halves the width and
height. YOLO looks for objects on three grids made at different depths:

```
input 640 × 640
  ├── stride 8  ─► 80 × 80 grid, each cell covers  8 ×  8 px  ◄── small objects
  ├── stride 16 ─► 40 × 40 grid, each cell covers 16 × 16 px  ◄── medium
  └── stride 32 ─► 20 × 20 grid, each cell covers 32 × 32 px  ◄── large
```

Each cell looks at its patch of the image and predicts the boxes there.
On the finest grid a cell covers 8 × 8 px. A line of text under 8 px tall is
less than one cell high there, so the model has almost nothing to work
with. That's why [`box_stats.py` counts date boxes under 8
px](../../scripts/box_stats.py#L59).

**What we measured** ([`results/m0_expdate_stats.md`](../../results/m0_expdate_stats.md)):

| Date box short side, median | Real train | Synthetic |
|---|---:|---:|
| at 640 px input | 16 px (2 cells tall) | 27 px |
| at 1280 px input | 32 px (4 cells tall) | 53 px |
| share under 8 px at 640 | 0.1% | 0.9% |

So 640 works but is tight. 1280 makes the dates twice as tall, but costs
**four times** the computation, because the number of pixels grows with
the square of the side. That's why M1 tried both on the validation photos
instead of guessing ([`m1.md` §2.7](m1.md#27--model-size-vs-speed)).

**In our code.**
[`box_stats.py`, lines 33–38](../../scripts/box_stats.py#L33-L38) turns
each box back into pixels and works out its short side at each input
size: `min(w, h) * n / max(s.width, s.height)`. Why the **short** side?
For a normal date that's its height, which is how tall the characters
are. For a sideways date it's the width, which is again the character
height. Either way, it's character height that decides whether the date
can be read.

> **Try it** (continues from 1.2):
>
> ```python
> w_px, h_px = X2 - X1, Y2 - Y1                    # 312, 47
> for n in (640, 1280):
>     scale = n / max(s.width, s.height)
>     print(n, round(w_px * scale, 1), round(h_px * scale, 1))
> # 640  137.2 20.7
> # 1280 274.5 41.3
> ```

## 2. Boxes and labels: detection basics

### 2.1 ★ Bounding boxes, and their three formats

A **bounding box** is the smallest upright rectangle around something.
The same box can be written down in three ways, and M0 uses all three:

| Format | The 4 numbers | Used by | test_00001's date |
|---|---|---|---|
| Pixel corners | `x1 y1 x2 y2`, in pixels | ExpDate's JSON | `[638, 576, 950, 623]` |
| Normalised corners | the same, divided by width or height | **our code** (`Box.xyxy`) | `(0.4385, 0.5275, 0.6529, 0.5705)` |
| YOLO | `cx cy w h`: centre and size, 0 to 1 | Ultralytics' label files | `0.545704 0.548993 0.214433 0.043040` |

**Why our code keeps normalised corners inside.** With one format
everywhere, no function needs to know a photo's size to compare two boxes,
and resizing the photo doesn't change them. Pixels come back only to draw
([`contact_sheet.py`](../../scripts/contact_sheet.py#L46-L47)) or to
measure ([`box_stats.py`](../../scripts/box_stats.py#L33-L34)).

**Why YOLO wants fractions.** YOLO resizes every photo (§1.4). In pixels,
the box would have to be recalculated for every size. "The centre is
54.6% of the way across" stays true at any size.

**Why YOLO wants centre and size.** That's how YOLO itself predicts a box:
a centre point, then a width and a height. Labels written the same way can
be compared directly with what the model predicts.

**In our code**, the path a box takes:

1. **Pixels → normalised:**
   [`expdate.normalise()`, lines 67–75](../../src/bestbefore/expdate.py#L67-L75)
   divides each `x` by the width and each `y` by the height, then
   **clips** to 0..1. A few ExpDate boxes stick out past the photo's edge
   by a pixel; [`check_expdate.py` counts
   them](../../scripts/check_expdate.py#L26-L29).
2. **Normalised corners → YOLO:**
   [`to_yolo()`, lines 13–15](../../src/bestbefore/yolo.py#L13-L15). The
   centre is the average of the two edges and the size is their
   difference.
3. **YOLO → corners:**
   [`from_yolo()`, lines 18–20](../../src/bestbefore/yolo.py#L18-L20). Each
   edge is the centre plus or minus half the size.
4. **One line per box:**
   [`label_lines()`, lines 23–32](../../src/bestbefore/yolo.py#L23-L32)
   skips boxes with zero width or height (they can't be learned from) and
   counts them. `:.6f` keeps 6 decimals, which is about a thousandth of a
   pixel on these photos.

**A worked example, by hand.** The date in `test_00001.jpg` (1455 × 1092
px) is `[638, 576, 950, 623]`:

```
centre_x = (638 + 950) / 2 / 1455 = 794   / 1455 = 0.545704
centre_y = (576 + 623) / 2 / 1092 = 599.5 / 1092 = 0.548993
width    = (950 − 638)     / 1455 = 312   / 1455 = 0.214433
height   = (623 − 576)     / 1092 = 47    / 1092 = 0.043040
class    = date            = 0
```

And the real line in `data/expdate/yolo/labels/real-test/test_00001.txt`
is `0 0.545704 0.548993 0.214433 0.043040`. The same numbers.

**Checking the conversion.** A conversion bug is silent (§3.4): swap x
and y, and YOLO trains happily on wrong boxes. So
[`expdate_to_yolo.py`, lines 65–74](../../scripts/expdate_to_yolo.py#L65-L74)
reads every label file back, converts it to pixels again and compares it
with the original. The worst difference over all 13,625 photos was
**0.003 px**, which is just rounding.
[`tests/test_yolo.py`](../../tests/test_yolo.py#L9-L15) does the same
round trip on three boxes in under a second.

### 2.2 ★ Labels and classes: a model learns only what the labels show

A model learns by copying the answers someone wrote down. Those answers
are the **labels** (or *annotations*). This is called *supervised
learning*. It means a model can only learn what the labels show, and it
learns labelling mistakes just as faithfully as the truth.

In ExpDate, a person drew a box on everything interesting and gave each
box a **class** (a category). In the JSON a test photo looks like this
(shortened from [`datasets.md`](../datasets.md)):

```json
"test_00001.jpg": {"height": 1092, "width": 1455, "ann": [
  {"cls": "exp", "bbox": [638, 576, 950, 623], "transcription": "2021.08.03",
   "dmy_ann": [ ...the day, month and year boxes inside the date... ]}]}
```

| Class | What it is | Example | Our class number |
|---|---|---|---|
| `date` | a printed date | `2020.12.12` | 0 |
| `exp` | the expiry date (test photos only) | `2021.08.03` | 0 (see below) |
| `due` | the word that announces an expiry | `EXP`, `Best before` | 1 |
| `prod` | the word that announces manufacture | `MFG` | 2 |
| `code` | a batch or lot code | `L22420` | 3 |

**Why `exp` becomes plain `date`**
([`yolo.py`, lines 6–10](../../src/bestbefore/yolo.py#L6-L10)). The
detector's only job is to *find* dates. Working out which one is the
expiry is the reader's job, in M3. The training photos have no `exp`
class at all, so a detector couldn't learn it anyway.

**Three lessons from our own labels:**

1. **Rare classes are learned worst.** Real train has 1,244 `date` boxes
   but only 100 `prod` boxes. That's called *class imbalance*. It's fine
   for us, since we mostly care about dates, but it's why the per-class
   scores in M1 differ.
2. **What isn't in the labels can't be learned.** 0% of real date boxes
   are taller than wide, so ExpDate has no sideways dates, and a detector
   trained on it has never seen one. The synthetic photos pair PROD and
   EXP dates at random, so they teach *where* dates are but not *which*
   one is the expiry. Both lessons shape M2.
3. **Every photo needs its labels, and every label its photo.**
   [`load_split()`, lines 46–51](../../src/bestbefore/expdate.py#L46-L51)
   stops if any photo has no annotation, or the other way round. A photo
   missing its label file is a silent wrong lesson: YOLO treats it as
   "nothing here", and so learns that a visible date is background.

### 2.3 ★ IoU: how a box gets scored

To decide whether a detector "found" the date, its box is compared with
the labelled box using **IoU** (*Intersection over Union*):

```
IoU = area where the two boxes overlap / area covered by either box
```

IoU is 1.0 when the boxes are identical and 0.0 when they don't touch.
The usual rule is that **IoU ≥ 0.5 counts as found**. That threshold is a
convention from the PASCAL VOC benchmark. It's loose enough to forgive the
small differences in where two people would draw the same box.

**Step by step**, with boxes written as `[x1, y1, x2, y2]`:

```
label box    A = [100, 50, 300, 90]     200 wide × 40 tall
detector box B = [120, 55, 310, 95]     190 wide × 40 tall

 A ┌──────────────────────┐
   │   ┌──────────────────┼──┐
   │   │     overlap      │  │ B
   └───┼──────────────────┘  │
       └─────────────────────┘
```

1. The overlap starts at the **larger** left edge and ends at the
   **smaller** right edge: `max(100, 120) = 120` to `min(300, 310) = 300`,
   so it's **180** wide.
2. The same from top to bottom: `max(50, 55) = 55` to `min(90, 95) = 90`,
   so it's **35** tall.
3. Overlap area: `180 × 35 = 6,300`.
4. Each box's area: A is `200 × 40 = 8,000`, B is `190 × 40 = 7,600`.
5. Union: `8,000 + 7,600 − 6,300 = 9,300`. The overlap is subtracted once
   because adding the two areas counts it twice.
6. IoU: `6,300 / 9,300 = 0.68`, which is above 0.5, so it's **found**.

If the boxes don't touch, step 1 or 2 gives a negative width. Treat it as
0, which makes the IoU 0.

**Why the box rule matters (the main Part A finding).** Looking at the
zoomed contact sheets, an ExpDate date box covers **only the date
value** (`2021.08.03`), not the word before it (`EXP:`) and not a time
after it. Suppose the detector learns that rule and draws a box 100 px
wide and 20 px tall around the date, but on a store photo someone labelled
`Best before: 15/08/2027`, a box 230 px wide:

```
overlap = 100 × 20 = 2,000
union   = 230 × 20 = 4,600
IoU     = 2,000 / 4,600 = 0.43   →  below 0.5  →  counted as a MISS
```

The detector was right but gets marked wrong, only because the two sets
were labelled with different rules. That's why the store photos in Part B
must use ExpDate's rule.

**In our code.** M1 has the real one:
[`detection_eval.iou()`, line 33](../../src/bestbefore/detection_eval.py#L33).

> **Try it**: write `iou(a, b)` yourself **before** opening
> `detection_eval.py`. Check it gives `0.677...` on the boxes above, `0.0`

### 2.4 ○ Expiry dates as data

The true expiry is stored as an
[`Expiry(year, month, day)`, lines 27–44](../../src/bestbefore/samples.py#L27-L44).
`day` is `None` when the pack prints only a month (`APR 2031`). This is

- `__post_init__` refuses impossible dates (month 13, 31 February) using

- [`parse_month()`](../../src/bestbefore/samples.py#L58-L64) accepts
  `08`, `AUG` and `August`.
  [`parse_year()`](../../src/bestbefore/samples.py#L67-L72) turns `27`
  into `2027`.
- [`expiry_from_parts()`, lines 78–96](../../src/bestbefore/expdate.py#L78-L96)
  builds the expiry from ExpDate's day / month / year boxes. If the year
  or month is missing, it returns `None`, and that photo is left out of
  reading scores and counted, instead of guessed.

## 3. Data you can trust: ML method

### 3.1 ★ Train, validation and test

Think of a student preparing for an exam:

| Split | Exam analogy | What happens to it |
|---|---|---|
| **Train** | homework with the answers at the back | the model learns from it |
| **Validation** | practice tests | you check progress and choose settings on it ("train 50 rounds or 100?") |
| **Test** | the final exam | used **once**, at the end, for the real score |

**The deep part: why even *looking* at the test set hurts.** You might
think the test set is safe as long as the model never trains on it. It
isn't. Every decision you make by looking at a score (which model size,
how many epochs, which threshold) fits your choices a little more to the
photos that produced that score. Make 20 such decisions on one set and
its score becomes too optimistic. The validation set exists to absorb
that: it gets "used up" by your choices. The test set stays untouched, so
its score stays honest.

**Our splits:**

```
ExpDate Products-Real train (1,102) ─┬─► train_real.txt  (937) ─┐ M1 learns from these
                                     └─► val.txt         (165)  │ and picks settings on val
ExpDate Products-Synth (11,858) ─────────► train_synth.txt ─────┘
ExpDate Products-Real test (665) ────────► test.txt            scored once (M1 D2)
Store photos (99) ───────────────────────► frozen test set     scored once per model (Part B)
```

ExpDate came with only train and test, so we made validation out of
train. Taking it from test would break the rule. 15% is a usual share
(people pick 10 to 20%): 165 photos give a steady score while 937 are
left to learn from.

**In our code:**

- [`expdate_to_yolo.py`, line 28](../../scripts/expdate_to_yolo.py#L28)
  sets the share, and
  [line 52](../../scripts/expdate_to_yolo.py#L52) picks the 165 at random
  with seed 0.
- [Lines 76–80](../../scripts/expdate_to_yolo.py#L76-L80) put each photo
  in its list, and
  [lines 91–93](../../scripts/expdate_to_yolo.py#L91-L93) tell YOLO which
  list is which.
- [`sets.py`, lines 16–18](../../src/bestbefore/sets.py#L16-L18) rebuilds
  the validation set from `val.txt`. That file is the one record of which
  photos are validation, so it must never be regenerated with a different
  seed.

○ **A subtle trap: near-duplicates.** If the same photo, or the same pack,
were in both train and validation, validation would look better than it
should. We checked this in
[`experiments/expdate-near-duplicates`](../../experiments/expdate-near-duplicates/README.md):

- **No copies between real train, validation and test.** Test is clean,
  so M1's test result stands.
- **One validation photo, `img_00277.jpg`, is reused 14 times in the
  synthetic training photos:** ExpDate's synthetic set erased its real
  date and printed fake ones on top. That makes validation optimistic by
  at most 1 photo of 165, which changes none of M1's choices, so nothing
  was retrained.
- **2 validation photos show the same product as a train photo** (a
  different bottle or cup). That's normal for photos taken in shops.

The check used two kinds of fingerprint: SHA-256 for exact copies, and a
*perceptual hash* for near copies. A perceptual hash shrinks a photo to a
tiny grey grid and records which pixels are brighter than their
neighbours, so it barely changes when a photo is resized or recompressed.

### 3.2 ★ Data leakage

**Data leakage** is any way information from the test data reaches the
model or your choices. The score then lies, usually upwards, and nothing
warns you. It's the most common mistake in ML projects, and reviewers look
for it first.

| Kind of leak | How it could happen here | How we stop it |
|---|---|---|
| Training on test data | a store photo ends up in a training list | store photos stay in their own folder and are never converted to YOLO or put in any training list |
| Tuning on the test set | picking the confidence threshold from store results | thresholds are chosen on validation only (the M1 rule) |
| Designing by looking at the test set | writing the date regex while reading test transcriptions | C1 writes the regex from **train** transcriptions and freezes it before any test run |
| Changing the test set | relabelling a store photo after seeing a model fail on it | the frozen test set (§4.1): any change is a new version with a written reason |

### 3.3 ★ Domain shift

A **domain** is the kind of data: where it came from and what it looks
like. **Domain shift** means the data a model is tested on differs from
the data it learned from. A model can score very well on its own kind of
data and badly on a new kind, and you only find out by testing on the new
kind.

We have three domains:

| | Synthetic ExpDate | Real ExpDate | Store photos |
|---|---|---|---|
| Made by | a computer | photos of packs, many of them Korean | staff phones in the retailer's Indian stores |
| Date formats | random | half are `YYYY.MM.DD` | 15 formats, ranges, "24 months from mfg" |
| Sideways dates | 0.5% | 0% | 17.6% of date boxes |
| Median date box, % of photo | 1.33% | 0.46% | 0.19% |

**Why this matters for your results.** M1's mAP of 0.993 is on ExpDate's
test split, the **same domain** it trained on. It shows the detector
learned ExpDate. It doesn't show the detector works in your stores. The
store test set measures exactly that gap, and M2 tries to close it with
synthetic data that looks like the store packs.

Real vs synthetic is a smaller shift of the same kind: synthetic dates
are about **three times** larger by area (1.33% vs 0.46%), so they're
easier, and a model trained only on them may struggle with real ones.
That's why M1 trains on both, and why the synthetic-data experiment
measures what they add instead of assuming it.

**How M0 measured it.** In B2, `box_stats.py store real-test` put the
store photos' date sizes next to ExpDate's
([`results/m0_store_stats.md`](../../results/m0_store_stats.md)). That
turned "the store photos look different" into numbers (§4.6).

### 3.4 ★ Look at the data before trusting it: silent bugs

There are two kinds of bug:

- A **loud** bug crashes. You see it, and you fix it.
- A **silent** bug gives wrong numbers with no error: x and y swapped, a
  photo opened sideways, a label off by one class. Training still runs,
  the loss still goes down, the results just come out worse, and you
  blame the model.

ML pipelines are full of silent bugs, so M0 uses three defences:

1. **Look.** [`contact_sheet.py`](../../scripts/contact_sheet.py) draws
   the boxes. [`photo_tile()`](../../scripts/contact_sheet.py#L41-L51)
   draws every box on a thumbnail, and
   [`date_tiles()`](../../scripts/contact_sheet.py#L54-L78) zooms in on
   each date together with its neighbours and its transcription. The
   photos are picked at random with a seed
   ([line 118](../../scripts/contact_sheet.py#L118)), not just the first
   50, which might all be alike. The box rule in §2.3 was found by looking
   at these sheets.
2. **Count, and compare with what you expect.**
   [`check_expdate.py`](../../scripts/check_expdate.py#L18-L44) prints
   counts per class, EXIF flags, size mismatches and boxes outside the
   photo, and those counts were compared with the paper's (1,102 / 665 /
   about 12,000). The plan's rule: if they differ, write down the real
   numbers. Don't "fix" them.
3. **Round trips.** Convert, convert back, and compare with the start
   ([§2.1](#21--bounding-boxes-and-their-three-formats)).

> **Try it**: make a contact sheet of photos you haven't seen yet.
>
> ```bash
> python scripts/contact_sheet.py --set real-val --n 30 --seed 7
> ```
>
> It prints a folder under `results/runs/`. Open `dates.jpg` and write
> down one thing that surprises you.

### 3.5 ○ Seeds

The 165 validation photos were picked **at random**, so they're a fair
sample. But computers make "random" choices from a starting number called
a **seed**. Same seed, same choices, every time, so anyone who reruns the
script with seed 0 gets the same 165 photos.

[`random.Random(seed)`](../../scripts/expdate_to_yolo.py#L52) makes a
*private* random generator. Other code using Python's shared `random`
can't change our pick.

### 3.6 ○ Reading a stats table: medians and percentiles

`box_stats.py` reports `p10 / median / p90` rather than an average:

- The **median** (p50) is the middle value: half the boxes are smaller,
  half are bigger.
- **p10** is the value 10% of boxes fall below; **p90**, the value 90%
  fall below.

The median is used instead of the average because a few huge boxes would
drag the average up (synthetic photos range from 163 to 5,182 px), while
the median doesn't move. For real-train date boxes, the area is
`0.29 / 0.46 / 0.97`% of the photo: most dates are a tiny part of the
frame.

## 4. The store test set (Part B)

Done on 2026-10-21. The 99 photos were labelled in Label Studio, imported
and checked (B2), and frozen as **v1** (B3). Counts:
[`results/store_test_set.md`](../../results/store_test_set.md).

### 4.1 ★ Why the test set is frozen

The store test set is 99 photos, **87 of them with an expiry** in frame,
each with the expiry as printed, tight boxes around every date, and one
failure tag. It's the most valuable thing in the project: it's the only
data from the real use, and nobody else has it.

**Frozen** means that once a model has been scored on it, it never
changes. If labels could change after you've seen results, you could
quietly "fix" the photos your model gets wrong, and your scores would
creep up without the model getting better. That's leakage (§3.2).

**In our code.**
[`freeze()`, lines 90–96](../../src/bestbefore/store.py#L90-L96) copies
every label and adds its photo's SHA-256 (§4.3).
[`read_test_set()`, lines 99–118](../../src/bestbefore/store.py#L99-L118)
does the reverse on every load: it hashes the file and compares it with
`TEST_SET_SHA256`, which sits in the code on
[line 50](../../src/bestbefore/store.py#L50), so it's in git. Then it
hashes all 99 photos. If anything differs, it stops. All of that takes
about 0.2 s.

Why keep the hash **in git** and the file **out of it**? The labels are
the retailer's data, so they stay on the laptop. The hash gives nothing
away, yet it pins down the file exactly: if the code says
`7b9a4043…` and the file hashes to anything else, the file was changed.

A real mistake is fixed only as a new version (`v2`):
[`freeze_store_test_set.py`](../../scripts/freeze_store_test_set.py)
refuses to overwrite v1, and a v2 needs `--why`, which goes into the
history at the bottom of `results/store_test_set.md`. Then every
baseline is rerun.

> **Try it.** Change one word in a copy of the frozen file, and watch the
> loader refuse it.
>
> ```python

>

### 4.2 ★ Failure tags: one number hides the story

Each photo gets **one tag** saying what makes it hard: `other-face`,
`sideways`, `curved`, `dot-matrix`, `small-print` or `clean`.

**Why break results down.** A made-up example:

| Tag | Photos | Read right |
|---|---:|---:|
| clean | 20 | 19 |
| dot-matrix | 15 | 6 |
| sideways | 8 | 1 |
| **all** | **43** | **26 (60%)** |

"60%" tells you nothing about what to fix next. The table tells you:
sideways dates. That's why `CLAUDE.md` says success is a table by failure
type, not one headline number.

**Why a fixed order.** A curved dot-matrix cap is both `curved` and
`dot-matrix`. So each photo takes the **first** tag that applies, in the
order `other-face` → `sideways` → `curved` → `dot-matrix` → `small-print`
→ `clean`. Geometry comes first, because a bent or turned line breaks
*finding* the text before the font matters. A fixed order means two
people, or you on two different days, give the same photo the same tag.

**Why `other-face` is left out of reading accuracy.** If the expiry is on
another face of the pack, no reader could get it from this photo. That's
a capture problem, not a reading problem.

**The real tags (v1):**

| Tag | Photos | With an expiry |
|---|---:|---:|
| other-face | 12 | 0 |
| sideways | 16 | 16 |
| curved | 0 | 0 |
| dot-matrix | 21 | 21 |
| small-print | 17 | 17 |
| clean | 33 | 33 |

No date on a cap or jar visibly bends its line, so `curved` is empty. The
row stays in every table at 0, so a reader can see it was looked for.

**Small numbers.** With 16 sideways photos, one photo is about 6 points.
So results are reported as `k/n` (`3/16`), not only as percentages, so
the reader can see how little data stands behind each number.

### 4.3 ○ SHA-256 fingerprints

A **hash** like SHA-256 turns any file into a 64-character code, its
fingerprint. The same file always gives the same code; change one byte
and the code changes completely.

[`sha256()`, lines 37–42](../../scripts/download_expdate.py#L37-L42)
reads the file 1 MB at a time, so a 1 GB zip doesn't need 1 GB of memory.
[Lines 53–55](../../scripts/download_expdate.py#L53-L55) stop the script
if a download doesn't match the recorded fingerprint, which proves the
laptop and the cluster have exactly the same ExpDate. The store's
[`sha256()`, lines 71–73](../../src/bestbefore/store.py#L71-L73) does the
same job with `hashlib.file_digest`, which reads in chunks for you
(Python 3.11 and later).

### 4.4 ★ Check labels before you trust them

Hand labels have mistakes: a typo in a year, a box with the wrong label,
an expiry typed but never boxed. Nothing crashes on a wrong label. It
just makes every later score a little wrong. So the import runs checks
first, and writes `labels.json` only if all of them pass.

| Check | What it catches | Code |
|---|---|---|
| 1. every photo labelled once | a skipped or doubled photo | [`check_photos()`](../../src/bestbefore/store_import.py#L123-L129) |
| 2. dates parse, years 2024–2035, mfg before expiry | `2207` for `2027`, day and month swapped | [`check_dates()`](../../src/bestbefore/store_import.py#L139-L154) |
| 3. expiry, tag and boxes agree | an expiry typed but not boxed; `other-face` with an expiry | [`check_consistency()`](../../src/bestbefore/store_import.py#L157-L175) |
| 4. agrees with Scanify's labels | a misread date, on either side | [`check_scanify()`](../../src/bestbefore/store_import.py#L188-L202) |
| 5. drawn on the upright photo | boxes on the sideways view (§1.3) | [`check_orientation()`](../../src/bestbefore/store_import.py#L205-L215) |

Each check returns **a list of problems**, not the first one it finds, so
one run shows everything to fix
([the loop in the script, lines 47–66](../../scripts/import_store_labels.py#L47-L66)).

**Check 4 is two labellers agreeing.** Scanify's 49 labels were typed
from the retailer's document; yours were typed from the photos. When two
people label on their own and agree, both are probably right. If you had
copied Scanify's, the check would compare a list with itself and prove
nothing. **All 49 agreed.**

One subtlety, in
[`same_expiry()`, lines 178–185](../../src/bestbefore/store_import.py#L178-L185):
Scanify turns a month-only expiry (`APR 2031`) into the last day of the
month (`30/04/31`). Your label keeps `2031-04`. So the day is compared
only when your label has one. Without that, every month-only pack would
look like a disagreement.

**What the checks found:** checks 1 to 5 all passed on the first export.
Check 5 had real work to do, since 46 photos carry an EXIF flag.

### 4.5 ★ A tag you can recompute beats a tag by eye

The plan's rule for `small-print` was "roughly, the date is shorter than
1.5% of the photo's long side". Check 6 measured it from your boxes,
in [`print_height()`, lines 220–225](../../src/bestbefore/store_import.py#L220-L225):
the expiry box's height in pixels, divided by the photo's long side.

It found that **20 of the 37 photos tagged `small-print` were above
1.5%** (1.52% to 2.76%), while every `clean` photo was above it too, from
1.99%. By eye, "small" had drifted to about 2 to 2.8%, with an overlap:
some 2.1% dates were `clean`, some 2.4% ones `small-print`. That isn't
carelessness. Judging size by eye across 99 photos, over two sittings,
simply drifts. Researchers call the agreement between labellers (or one
labeller on two days) **inter-rater reliability**, and size judgements
score badly on it.

The fix: where a tag *can* be measured, measure it.
[`print_tag()`, lines 228–235](../../src/bestbefore/store_import.py#L228-L235)
now decides `small-print` vs `clean` from the box. Anyone can rerun it
and get the same tags. It only touches those two tags: `sideways` and
`dot-matrix` come earlier in the order and stay as you set them.

## 5. Baselines and scoring (Part C)

C1 (scoring and baseline A) was done on 2026-10-21; C2 (baseline B) and
C3 (the table) are still to do.

### 5.1 ★ Baselines

A **baseline** is the score of a simple method that already exists: the
number to beat. Without one, "my model reads 70%" means nothing. 70%
compared with what?

We measure two:

- **A: RapidOCR off the shelf, plus a simple date regex.** It picks the
  *latest* date it finds, because an expiry comes after the manufacture
  date. Anyone can reproduce it.
- **B: Scanify's reader.** The same RapidOCR version (1.2.3) plus
  Scanify's resizing, sharpening and rules.

Because A and B use the same OCR, **the gap between them is exactly what
Scanify's rules add**. Changing one thing at a time like this is called
an **ablation**. M3 is only worth it if it beats B.

**Reproduce before you compare.** B is already known to read 32 of the
44 right, with 12 missed and 0 wrong. C2 must get exactly that before
it's run on anything else. If it doesn't, assume the bug is in our
harness, not in Scanify.

### 5.2 ★ Right, wrong or none: not all errors cost the same

Every photo's reading gets one of three outcomes:

| Outcome | Meaning | What it costs in the store |
|---|---|---|
| **right** | the expiry matches | nothing |
| **none** | no date returned | staff type it in by hand: a few seconds |
| **wrong** | a different date returned | `08/2027` read as `08/2021` marks a good batch as expired, or an expired batch as good, and **nobody notices** |

A wrong read is much worse than no read, so the table keeps
**separate** right / wrong / none columns instead of one accuracy number.
A model that turns 5 "none" into 3 "right" and 2 "wrong" isn't
automatically better.

Two scoring details:

- **Month-only packs.** If the pack prints `APR 2031`, matching month and
  year is enough. Scanify answers with the last day of the month, and
  that must still count as right.
- **Reading the manufacture date as the expiry is `wrong`**, not
  "nearly right".

M1 uses the same idea when it chooses its confidence threshold by what a
miss costs (see `m1.md`).

**In our code.** [`score()`, lines 17–26](../../src/bestbefore/scoring.py#L17-L26)
is the whole rule, in four steps: no date is `none`; a different year or
month is `wrong`; a pack with no day printed is then `right`; otherwise
the day decides. Every reader, from baseline A to M3's model, is scored
by this one function, so their numbers can be compared.

### 5.3 ★ Writing rules without peeking at the test

Baseline A needs rules for turning OCR text into dates. The trap: if you
write them while looking at the test photos, you'll add a rule for every
format the test happens to contain, and A will score better than it
would on any new photo. That's tuning on the test set (§3.2), done by
hand.

So the rules in
[`dates.py`](../../src/bestbefore/dates.py) were written from two
sources only: the 1,244 date transcriptions in ExpDate's **real-train**
split, and the format list in `CLAUDE.md`. Then they were frozen (the
tests pass, the code is fixed) **before** baseline A read a single test
photo. A store format seen in the stats table, like `DDMMYYYY`, was
deliberately left out, because it's known only from the store photos.

**Dates are ambiguous.** `04/12/2026` is 4 December in India and
12 April in the US. `21.08.15` could be 21 August 2015 or 15 August 2021.
A rule has to pick, and the training data can say which pick is right
more often:

> **Try it.** How do real-train's dates with three 2-digit parts and dots
> (`21.08.15`) start?
>
> ```python
> import re
> from collections import Counter
> from bestbefore import expdate
> texts = [b.text for s in expdate.load_split("real-train") for b in s.boxes
>          if b.label == "date" and b.text]
> dotted = [t for t in texts if re.fullmatch(r"\d\d\.\d\d\.\d\d", t)]
> print(len(dotted), Counter(int(t[:2]) for t in dotted).most_common(5))
> ```
>
> ```
> 147 [(21, 82), (20, 30), (22, 14), (19, 11), (14, 2)]
> ```
>
> 137 of the 147 start with 19 to 22, which are years (2019 to 2022), and
> the last part runs from 1 to 31, like a day. So these Korean dates are
> year first, and
> [the `YY.MM.DD` pattern, line 49](../../src/bestbefore/dates.py#L49)
> reads them that way. With slashes, the rule stays day first, as Indian
> packs print it.

**How the rules work.** Each pattern in
[`_PATTERNS`, lines 42–56](../../src/bestbefore/dates.py#L42-L56) is a
regular expression plus the orders its parts may be read in, most likely
first. [`_make()`, lines 71–82](../../src/bestbefore/dates.py#L71-L82)
tries each order and keeps the first that makes a real date between 2015
and 2039. So `08/25/2027` can't be day first (there's no month 25) and
becomes 25 August.

Where matches overlap,
[`find_dates()`, lines 94–103](../../src/bestbefore/dates.py#L94-L103)
keeps the longest: `15/08/2027` beats the `08/2027` inside it. A match
that turns out not to be a real date still takes its place. Without
that, `29/02/2027` (not a leap year) would quietly come back as
"February 2027": a wrong answer dressed up as a careful one. A test
caught exactly this before any test photo was read.

Finally, [`latest()`, lines 106–110](../../src/bestbefore/dates.py#L106-L110)
picks the expiry: the latest date found. It needs no "EXP" or "MFG"
words, which makes it simple, and it has known failures: a pack showing
only a mfg date gets that date read as the expiry, which scores `wrong`.

**Coverage on the training dates.** The rules read 1,211 of the 1,244
real-train transcriptions (97%) whole. Of the 33 misses, 31 are two-part
dates like `08.27`, skipped on purpose: without a 4-digit year, `08.27`
is as likely a price or a weight.

### 5.4 ★ What baseline A scored, and why it fails

[`rapidocr_regex.py`](../../src/bestbefore/baselines/rapidocr_regex.py)
is the whole of baseline A: RapidOCR reads every text line in the upright
photo, `find_dates()` runs on each line, and `latest()` picks one.
[`run_baseline.py`](../../scripts/run_baseline.py) scores every photo and
writes one JSON line per photo, so any number can be traced back to the
photo it came from.

| Baseline A | n | right | wrong | none |
|---|---:|---:|---:|---:|
| ExpDate test | 655 | 502 | 28 | 125 |
| Store: sideways | 16 | 6 | 5 | 5 |
| Store: dot-matrix | 21 | 7 | 0 | 14 |
| Store: small-print | 17 | 14 | 2 | 1 |
| Store: clean | 33 | 22 | 5 | 6 |
| **Store: all** | **87** | **49** | **12** | **26** |

**The headline hides the story** (§4.2 again): dot-matrix is the wall,
7 of 21, and all 14 of its failures are `none`, because OCR sees no
date-shaped text at all. Small print, which sounds hard, scores 14 of 17:
whole-photo OCR at full resolution copes with it.

**Error analysis: look at the failures, not just the count.** Every
failure has a cause, and the causes point at different fixes:

- **Store, `none` (26):** OCR found no date at all in every one. A
  better regex can't help; better *reading* can (M3).
- **Store, `wrong` (12):** every one is an earlier date than the truth,
  and the true expiry was never among the dates found. OCR missed the
  expiry, read the mfg date, and "latest date" had nothing better to
  pick. 5 of the 12 are packs that print only mfg + shelf life, which
  this rule can never get right.
- **ExpDate, `wrong` (28):** 16 are a month-only stub of a dated pack.

> **Try it.** Find those stubs.
>

> 16 of 28 wrong reads are the month of a dated pack

> ```
>
> (`None` is the 10 photos with no marked expiry.) OCR glued the day
> `07` to the `1` of the lot code. Now `2022.07.071` isn't a date: a
> digit touches its end. So the full-date pattern fails, and the
> month-only `YYYY.MM` pattern matches `2022.07` instead. In 14 of the 16

>

## 6. Engineering habits

All ○: quick reads, but worth mentioning in interviews.

- **Paths in `.env`.**
  [`config.py`, lines 13–23](../../src/bestbefore/config.py#L13-L23)
  reads `.env` and fails with a clear message naming any missing
  variable. The same code runs on the laptop and the cluster; only `.env`
  differs.
- **Run records.** [`start_run()`, lines 41–58](../../src/bestbefore/runs.py#L41-L58)
  writes a `run.json` with the command, git commit (and whether there were
  uncommitted changes), seed, settings and library versions. Any number in
  `results/` can be traced back to exactly what made it.
- **One shape for every dataset.**
  [`Sample`](../../src/bestbefore/samples.py#L47-L55) is the same for
  ExpDate and the store photos, and
  [`load_set()`](../../src/bestbefore/sets.py#L13-L19) loads either by
  name. The contact sheet, the stats and the baselines are each written
  once.
- **Symlinks instead of copies.**
  [`expdate_to_yolo.py`, lines 55–58](../../scripts/expdate_to_yolo.py#L55-L58)
  puts shortcuts in YOLO's `images/` folder instead of a second 1.7 GB
  copy. They store full paths on this laptop, so on the cluster the
  converter is rerun instead of the folder being copied.
- **Tests.** `pytest -q` runs every file in `tests/` in about a second.
  When code changes later, they say at once if something that used to
  work broke.
- **Data stays out of git.** It's too big, ExpDate has its own licence
  and home, and the store photos are private.

## Check yourself

<details>
<summary>1. A photo's numpy shape is (1092, 1455, 3). How wide is it, and what is the 3?</summary>

1455 px wide (numpy lists height first). The 3 is the colour channels:
red, green and blue.
</details>

<details>
<summary>2. Why does box_stats.py count date boxes under 8 px at 640?</summary>

YOLO's finest grid has cells 8 × 8 px (stride 8). A date shorter than
that is less than one cell high, so the model has almost nothing to work
with.
</details>

<details>
<summary>3. Why can't we use the test photos to choose how long to train?</summary>

Every choice made by looking at test scores fits the model a little more
to those exact photos, like studying from the final exam. The test score
then looks better than the model really is. Validation is for choices.
</details>

<details>
<summary>4. A box is [100, 50, 300, 90] in a 1000 × 500 photo. What's its YOLO line, if it's a date?</summary>

centre_x = 200 / 1000 = 0.2, centre_y = 70 / 500 = 0.14, width = 200 /
1000 = 0.2, height = 40 / 500 = 0.08:

`0 0.200000 0.140000 0.200000 0.080000`
</details>

<details>
<summary>5. Your detector finds a date perfectly, but the store label also includes the word "EXP:". Why might it count as a miss?</summary>

The labelled box is wider than the detector's, so the IoU falls. Below
0.5, a correct find counts as a miss. That's why both datasets must use
the same box rule.
</details>

<details>
<summary>6. M1 scored mAP 0.993 on ExpDate test. Why isn't that the headline result?</summary>

Domain shift. ExpDate test is the same kind of data M1 trained on. The
store photos have other formats, sideways and curved dates and dot-matrix
print. Only the store test set shows whether the detector works where it
will be used.
</details>

<details>
<summary>7. Give two ways the store photos could leak into the results.</summary>

Any two of: training on them; choosing a threshold or setting by their
scores; writing the date regex while looking at them; relabelling a photo
after seeing a model fail on it.
</details>

<details>
<summary>8. Why keep "wrong" and "none" as separate columns?</summary>

They cost different amounts. No date means staff type it in. A wrong date
can mark a good batch as expired, or an expired one as good, without
anyone noticing.
</details>

<details>
<summary>9. ExpDate has 0% sideways dates. What happens if M1 trains only on ExpDate?</summary>

The detector has never seen a sideways date, so it will probably miss
them on the store photos. M2's generator adds sideways dates to fix
exactly that, and the M2 experiment measures whether it worked.
</details>

<details>
<summary>10. Why does every photo go through load_upright?</summary>

Phone photos are often stored sideways with an EXIF note saying how to
turn them. If one script follows the note and another doesn't, boxes land
in the wrong place with no error. One function for all photos means they
can never disagree.
</details>

## Glossary

| Word | Meaning |
|---|---|
| Ablation | changing one thing at a time to see what it adds |
| Annotation / label | the correct answer someone wrote down for an example |
| Baseline | the score of an existing simple method; the number to beat |
| Bounding box | the smallest upright rectangle around an object |
| Channel | one colour layer of an image (red, green or blue) |
| Class | the category a box belongs to (`date`, `due`, …) |
| Class imbalance | some classes have far more examples than others |
| Contact sheet | many small photos with their boxes drawn, on one page |
| Data leakage | test information reaching the model or your choices |
| Detection | finding *where* things are (boxes) |
| Domain shift | test data that differs from the training data |
| EXIF | extra information stored in a photo file, including "rotate me" |
| Failure tag | the one label saying what makes a store photo hard to read |
| Frozen test set | a test set that never changes once models are scored on it |
| Hash (SHA-256) | a file's fingerprint |
| IoU | the overlap of two boxes divided by the area they cover together |
| Letterboxing | resizing without stretching, filling the gap with grey |
| Median / percentile | the middle value / the value a given share falls below |
| Normalised coordinates | positions as fractions (0 to 1) of the photo's size |
| Recognition | reading *what* the text says |
| Seed | the starting number for "random" choices; same seed, same result |
| Stride | how far a CNN layer moves per step; stride 2 halves the size |
| Symlink | a shortcut file pointing to another file |
| Synthetic data | training examples made by a computer |
| Train / validation / test | learn from / choose settings on / final score, used once |
| `uint8` | a whole number from 0 to 255, how pixels are stored |
| YOLO | a fast family of detection models; Ultralytics is the library that trains it |
