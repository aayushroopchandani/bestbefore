## 1. Computer vision basics: how a CNN sees a photo

Start here. M0 §1 showed that a photo is a block of numbers
(height × width × 3). This section follows that block into the network.

### 1.1 ★ Convolution: a small filter that slides

A **convolution** takes a small grid of weights, the **filter** (or
*kernel*), slides it across the image, and at each position multiplies
the pixels under it by the weights and adds them up. The result is one
number per position. Do that everywhere and you get a new image, called a
**feature map**, that is bright wherever the image looks like the filter.

```
 image patch (one channel)     filter             result at this position
 ┌────┬────┬────┐          ┌────┬────┬────┐
 │ 10 │ 10 │200 │          │ -1 │  0 │ +1 │     (-10 + 0 + 200)
 ├────┼────┼────┤    ×     ├────┼────┼────┤   + (-10 + 0 + 200)   = 570
 │ 10 │ 10 │200 │          │ -1 │  0 │ +1 │   + (-10 + 0 + 200)
 ├────┼────┼────┤          ├────┼────┼────┤
 │ 10 │ 10 │200 │          │ -1 │  0 │ +1 │   a big number: "dark on the left,
 └────┴────┴────┘          └────┴────┴────┘    bright on the right" = an edge
```

That filter finds vertical edges, like the side of a printed `1`. Nobody
writes the filters by hand: they are **weights**, and training finds
them (§2).

Three facts about a real convolution layer:

- **Each filter covers all the input channels.** On a colour photo a 3×3
  filter is really 3×3×3: one 3×3 slice for each of red, green and blue.
- **A layer has many filters**, and each one makes its own feature map.
  So the output has as many channels as the layer has filters.
- **Stride** is how far the filter jumps each step. Stride 2 skips every
  other position, so the output is half as wide and half as tall.

**In our model.** The very first layer of `yolo11n` is **16 filters of
3×3×3, with stride 2**. A 640 × 640 × 3 photo goes in; a 320 × 320 × 16
block comes out: 16 feature maps, each half the size.

Its weights: 16 filters × 3 × 3 × 3 = **432**. The layer also has a
*batch norm* (○, below) with 2 numbers per filter, 32 more, so **464** in
all. That's exactly the `464` in the first row of the model table the
training log prints.

**In Ultralytics' code.** Every convolution in YOLO is a
[`Conv` block](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/nn/modules/conv.py#L48-L87):
a convolution, then batch norm, then an activation (§2.1). Its whole
`forward` is one line:
[`self.act(self.bn(self.conv(x)))`](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/nn/modules/conv.py#L87).

○ **Batch norm** rescales each feature map so its numbers stay in a
steady range (around 0, spread about 1) while training. Without it, the
numbers can grow or shrink layer after layer, and training gets slow and
unstable. You don't need more than that for M1.

### 1.2 ★ Feature maps and the three grids

A CNN repeats "convolve, shrink" many times. With each stride-2 layer the
map gets smaller and has more channels:

```
 photo         640 × 640 ×   3
 layer 0       320 × 320 ×  16    stride  2   edges, colour blobs
 layer 1       160 × 160 ×  32    stride  4   corners, short strokes
 ...                                          bits of characters
 layer 16       80 ×  80 ×  64    stride  8  ─┐
 layer 19       40 ×  40 × 128    stride 16   ├─► the three grids the
 layer 22       20 ×  20 × 256    stride 32  ─┘   detector predicts from
```

Two things change as you go deeper:

1. **Each cell covers more of the photo.** One cell of the stride-8 grid
   stands for an 8 × 8 px patch; one cell of the stride-32 grid for
   32 × 32 px. But because each layer's filters look at the previous
   layer's cells, a deep cell has really "seen" a much bigger area than
   its patch. That area is its **receptive field**.
2. **The features get more meaningful.** Early maps respond to edges;
   later ones to things like "a row of digits" or "a white label on a
   dark box". More channels means more kinds of thing it can record.

So the three grids split the work by size: the **fine** grid (80 × 80,
small cells) finds small objects, the **coarse** grid (20 × 20) finds
big ones. At 640 px a real ExpDate date is about **16 px tall**, two
cells of the fine grid ([m0 §1.4](m0.md#14--resizing-and-why-small-dates-are-hard-for-a-cnn)).
That's why tiny store-photo print is a risk (plan, Risks).

Add up the cells: 80 × 80 + 40 × 40 + 20 × 20 = **8,400**. YOLO makes a
prediction at every one of them, for every photo. §3 is about what each
prediction says and how 8,400 of them become a handful of boxes.

> **Try it**: watch a photo-sized block go through the M1 detector.
>
> ```python

> from ultralytics import YOLO
>
> net = YOLO(BEST).model.eval()           # the PyTorch network inside
> shapes = {}
> for i in (0, 1, 16, 19, 22):            # first two layers, and the 3 grids
>     net.model[i].register_forward_hook(
>         lambda mod, inp, out, i=i: shapes.__setitem__(i, tuple(out.shape)))
> with torch.no_grad():
>     out = net(torch.zeros(1, 3, 640, 640))   # 1 blank photo, 3 channels
> for i, s in shapes.items():
>     print(i, s)
> print(out[0].shape)
> ```
>
> ```
> 0 (1, 16, 320, 320)
> 1 (1, 32, 160, 160)
> 16 (1, 64, 80, 80)
> 19 (1, 128, 40, 40)
> 22 (1, 256, 20, 20)
> torch.Size([1, 8, 8400])
> ```
>
> PyTorch writes shapes as (batch, channels, height, width): channels come
> **before** height and width, unlike numpy's (height, width, channels)
> in M0. The last line is the whole output: 8 numbers at each of 8,400
> places. §3.1 explains the 8.

### 1.3 ○ Backbone, neck and head

The log prints `yolo11n` as 24 numbered layers. They fall into three
groups:

| Layers | Part | Its job |
|---|---|---|
| 0–10 | **backbone** | the CNN that turns the photo into feature maps, shrinking as it goes |
| 11–22 | **neck** | mixes the maps: it **upsamples** the deep, coarse maps (makes them bigger again) and **concatenates** them with earlier, finer ones |
| 23 | **head** (`Detect`) | turns each grid cell's features into box and class numbers (§3.1) |

Why the neck: deep maps know *what* things are but have lost *where*
exactly; early maps know *where* but not *what*. Joining them gives the
fine grid both. That's what the `Upsample` and `Concat` rows in the log
are.

You don't need the inside of the other blocks for M1. `C3k2` is a stack
of convolutions with a shortcut, `SPPF` pools over several sizes, and
`C2PSA` contains a small **attention** block, an idea you'll meet in M3.

## 2. Deep learning fundamentals: how a network learns

### 2.1 ★ A neuron, a layer, an activation, the forward pass

A **neuron** does three things:

1. multiplies each input by a **weight**,
2. adds them up, plus one more number, the **bias**,
3. passes the sum through an **activation function**.

```
 inputs   x = [0.2, 0.9, 0.4]
 weights  w = [1.5, -2.0, 0.5]       bias b = 0.1

 sum  z = 1.5×0.2 + (−2.0)×0.9 + 0.5×0.4 + 0.1 = 0.3 − 1.8 + 0.2 + 0.1 = −1.2
 ReLU(z) = max(0, z) = 0
```

The weights and biases are the **parameters**: the numbers training
changes. `yolo11n` has about **2.6 million** of them.

**Why the activation matters.** Without it, a neuron is just a weighted
sum, and a stack of weighted sums is still one big weighted sum: a
straight-line model, however many layers you stack. The activation bends
the line, so stacked layers can learn curved, complicated rules like
"this blob of strokes is a date".

- **ReLU**: `max(0, z)`. Negatives become 0, positives pass unchanged.
  Simple and fast.
- **SiLU**: `z × sigmoid(z)`. Almost the same shape as ReLU, but smooth,
  and it lets a little of the negative side through. **YOLO uses SiLU**
  ([`default_act = nn.SiLU()`](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/nn/modules/conv.py#L58)).

**A layer** is many neurons side by side, all reading the same inputs. A
convolution layer is a special layer: each filter is one neuron that is
**reused at every position** of the image, with the same weights. That
weight sharing is why a CNN needs so few parameters for a big photo.

**The forward pass** is running the input through every layer, in order,
to get the output: photo in, 8 × 8,400 numbers out. Predicting is just
the forward pass. Training is a forward pass, then the backward pass of
§2.3, over and over.

> **Try it**: one neuron, by hand and by PyTorch.
>
> ```python
> import torch
> x = torch.tensor([0.2, 0.9, 0.4])
> w = torch.tensor([1.5, -2.0, 0.5])
> z = (w * x).sum() + 0.1
> print(z)                              # tensor(-1.2000)
> print(torch.relu(z))                  # tensor(0.)
> print(torch.nn.functional.silu(z))    # tensor(-0.2778)
> ```
>
> Change one weight so that `z` is positive. What do ReLU and SiLU give
> now, and how close are they?

### 2.2 ★ Loss: one number for how wrong the model is

After a forward pass, the output is compared with the label. The **loss**
turns "how wrong" into **one number**: 0 means perfect, bigger means
worse. Training means making that number small. Different tasks use
different losses:

- **Regression** (predict a number, like a box edge): how far off was
  it? M1's box loss is built on IoU (§3.3).
- **Classification** (predict a category): **cross-entropy**. The model
  outputs a probability `p` for the right answer, and the loss is
  `−log(p)`.

Why `−log(p)`: it barely punishes a confident right answer, and
punishes a confident wrong answer hard.

| Model's probability for the right answer | Loss `−log(p)` |
|---:|---:|
| 0.9 | 0.105 |
| 0.5 | 0.693 |
| 0.1 | 2.303 |

YOLO uses **binary** cross-entropy (BCE): for each of the 4 classes, a
separate yes/no question ("is this a date? is this a `due` mark?"), each
with its own probability. §3.3 puts the whole detection loss together.

> **Try it**
>
> ```python
> import torch.nn.functional as F
> for p in (0.9, 0.5, 0.1):
>     print(p, F.binary_cross_entropy(torch.tensor(p), torch.tensor(1.0)))
> # 0.9 tensor(0.1054)
> # 0.5 tensor(0.6931)
> # 0.1 tensor(2.3026)
> ```

### 2.3 ★ Gradient descent and backpropagation

Training has to answer: **which way should each of the 2.6 million
weights move to make the loss smaller?**

Picture standing on a hillside in fog. You can't see the valley, but you
can feel which way the ground slopes under your feet. Take a small step
downhill; feel again; repeat. That's **gradient descent**:

```
new weight = old weight − learning rate × gradient
```

- The **gradient** of the loss with respect to a weight says how much
  the loss goes up when that weight goes up a tiny bit. Positive
  gradient: move the weight down. Negative: move it up.
- The **learning rate** is the size of the step.

**Backpropagation** is how the gradients are worked out. The loss
depends on the last layer, which depends on the layer before, and so on
back to the photo. The chain rule from calculus lets you walk that chain
**backwards**, once, and get the gradient of every weight in one pass.
You never write it: PyTorch records the forward pass and does it when
you call `loss.backward()`. In Ultralytics' training loop that's
[this line](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/engine/trainer.py#L564)
(the `scaler` around it is for half precision, §2.9).

> **Try it**: gradient descent on a model with one weight. The data
> follows `y = 3x`, the model is `y = w·x`, and `w` starts at 0. Can
> it find 3?
>
> ```python
> xs = torch.tensor([1.0, 2.0, 3.0, 4.0])
> ys = 3 * xs
> for lr in (0.01, 0.05, 0.15):
>     w = torch.tensor(0.0, requires_grad=True)
>     for step in range(20):
>         loss = ((w * xs - ys) ** 2).mean()   # forward pass + loss
>         loss.backward()                      # backpropagation: fills w.grad
>         with torch.no_grad():
>             w -= lr * w.grad                 # one gradient-descent step
>         w.grad.zero_()
>         if step in (0, 1, 4, 19):
>             print(lr, step, round(w.item(), 3))
> ```
>
> | Learning rate | after step 1 | step 2 | step 5 | step 20 |
> |---:|---:|---:|---:|---:|
> | 0.01 | 0.45 | 0.832 | 1.669 | 2.884 (still crawling) |
> | 0.05 | 2.25 | 2.812 | 2.997 | 3.0 (found it) |
> | 0.15 | 6.75 | −1.688 | 12.155 | −257.2 (blew up) |
>
> Too small and it crawls; too big and every step overshoots the valley
> further than the last. That's the whole reason learning rates,
> warmup and schedules (next) exist.
>
> Check the first step by hand: the gradient at `w = 0` is
> `mean(2x(wx − y)) = −6 × mean(x²) = −6 × 7.5 = −45`, so the step is
> `0 − 0.01 × (−45) = 0.45`.

### 2.4 ★ Learning rate, optimisers and warmup

**Optimisers** are recipes for turning gradients into steps.

- **SGD** (stochastic gradient descent) is the formula above, using the
  gradient from a small batch of photos instead of all of them: cheaper,
  and a bit noisy (that's the "stochastic").
- **Momentum** adds a memory: the step keeps some of the previous step's
  direction, like a ball rolling downhill that doesn't stop dead at
  every bump. Our runs use momentum of about 0.9.
- **Adam / AdamW** give every weight its own step size, bigger for
  weights whose gradients are small and steady, smaller for jumpy ones.
  AdamW is Adam with *weight decay* (○: a small pull of every weight
  towards 0, which discourages extreme weights).

**What our runs actually used.** We left Ultralytics' setting
`optimizer=auto`, which
[chooses by the number of training steps](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/engine/trainer.py#L1175-L1183):
more than 10,000 and it picks **MuSGD** with learning rate 0.01;
fewer and it picks **AdamW** with a learning rate from a formula
(0.002 × 5 / (4 + classes) = **0.00125** for our 4 classes). The log
shows both:

```
C1 runs, D1 seeds (12,795 photos):  optimizer: MuSGD(lr=0.01, momentum=0.9) ...
smoke test, C2 real-only (937):     optimizer: AdamW(lr=0.00125, momentum=0.9) ...
```

MuSGD is a recent Ultralytics optimiser that mixes SGD with one called
Muon. For this guide, treat it as SGD with momentum. That the choice
changed between C2's two runs matters, though: §4.6.

**Warmup.** At the start, the new class layer (§2.6) is random, so its
gradients are large and wild. Full-size steps then would damage the
good pretrained weights. So for the first **3 epochs** (2,400 batches),
the learning rate rises from 0 to its full value
([warmup code](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/engine/trainer.py#L519-L537)).

**Schedule.** After warmup the learning rate falls in a straight line,
to 1% of its start by the last epoch
([`self.lf`](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/engine/trainer.py#L268-L274),
with `lrf: 0.01` in
[the defaults](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/cfg/default.yaml#L94-L100)).
Big steps early to get near the valley, small steps late to settle in
it.

> **Try it**: the learning rate our `n640` run used, by epoch.
>
> ```python
> lr0, lrf, E = 0.01, 0.01, 100
> lf = lambda e: (1 - e / E) * (1 - lrf) + lrf     # Ultralytics' linear schedule
> for e in (0, 3, 50, 90, 99):
>     print(e, round(lr0 * lf(e), 5))
> # 0 0.01     (reached at the end of warmup)
> # 3 0.0097
> # 50 0.00505
> # 90 0.00109
> # 99 0.0002
> ```

○ Two more safety rails in the same loop:
[gradient clipping](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/engine/trainer.py#L907-L918)
caps how big one step can be, and an **EMA** (exponential moving
average) keeps a smoothed copy of the weights, averaged over recent
steps. The saved `best.pt` is that smoothed copy, which is a little
steadier than the raw weights.

### 2.5 ★ Batch, iteration, epoch

| Word | Meaning | In our `n640` run |
|---|---|---|
| **batch** | photos processed together in one forward + backward pass | 16 photos |
| **iteration** | one batch | 800 per epoch (12,795 ÷ 16, rounded up) |
| **epoch** | one pass over every training photo | 100 |
| **update** (optimiser step) | one change to the weights | every 4 batches: 200 per epoch, about 20,000 in all |

The last row is an Ultralytics detail worth knowing. It has a "nominal
batch size" of 64 (`nbs`), so with batches of 16 it **adds up the
gradients of 4 batches** before taking one step
([`accumulate`](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/engine/trainer.py#L321-L326),
[used here](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/engine/trainer.py#L600-L601)).
So each step is based on 64 photos, which makes it less noisy, while
only 16 photos have to fit in GPU memory at once. This is called
**gradient accumulation**.

Why batches at all? One photo at a time gives very noisy gradients, and
all 12,795 at once would never fit in memory. A batch is the compromise.

The losses printed per epoch in the log are averages over that epoch's
800 batches:

```
      Epoch    GPU_mem   box_loss   cls_loss   dfl_loss  Instances       Size

### 2.6 ★ Transfer learning and fine-tuning

A network with random weights knows nothing. To learn even what an edge
is, it would need far more photos than we have: 937 real photos can't
set 2.6 million weights from scratch.

So M1 starts from **pretrained weights**: `yolo11n.pt`, a YOLO already
trained by Ultralytics on **COCO**, a dataset of about 118,000 everyday
photos with 80 classes (`person`, `car`, `cup`, …).
[`fetch_pretrained.py`, line 23](../../scripts/fetch_pretrained.py#L23)
downloads it, and
[`detector.train()`, line 68](../../src/bestbefore/detector.py#L68)
starts from it.

**Why that helps with dates, which COCO doesn't have.** The early layers
learned edges, strokes, corners and textures. Those are the same in
every photo, printed dates included. Only the later layers are specific
to COCO's classes. **Fine-tuning** keeps training the whole network on
our photos, so the general layers are mostly kept and adjusted, and the
specific ones re-learn for dates. It's like a person who already reads
English learning a new font, instead of learning to read from nothing.

**The one layer that can't be reused.** COCO's last layer outputs 80
class scores; ours needs 4. The log shows it:

```
Overriding model.yaml nc=80 with nc=4
Transferred 493/499 items from pretrained weights
```

The 6 that didn't transfer are the final class layer at each of the 3
grids, a weight and a bias each. They start random and are learned from
scratch. That's the "random new layer" warmup protects (§2.4).

### 2.7 ○ Model size vs speed

| Model | Parameters | Computation per 640 px photo |
|---|---:|---:|
| `yolo11n` (nano) | 2.6 M | 6.5 GFLOPs |
| `yolo11s` (small) | 9.4 M | 21.5 GFLOPs |

A **GFLOP** is a billion multiply-and-add operations. More parameters
can learn finer detail but cost more memory and time, and on a phone
(M5) that matters. Input size costs in the same way: 1280 px has **4×**
the pixels of 640, so about 4× the computation.

C1 tried all four combinations. On ExpDate validation they all found 185
to 187 of the 187 dates, so the decision rule picked the cheapest,
`n640` (§4.5). Bigger only bought **tighter** boxes (§3.7).

### 2.8 ★ Data augmentation, and why flipping is off

**Augmentation** means training on randomly changed copies of each photo,
made fresh every time the photo is used. The model sees more variety
without anyone labelling more photos, so it copes better with new ones.
The changes must be ones that **could happen in real photos**, and the
boxes are moved along with the pixels.

Ultralytics' pipeline for every training photo
([`v8_transforms`](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/data/augment.py#L2870-L2909)),
with our settings:

| Step | What it does | Our setting |
|---|---|---|
| **Mosaic** | stitches 4 training photos into one 2 × 2 tile | on, except in the last 10 epochs |
| **Random affine** | shifts by up to ±10%, zooms by up to ±50% | default |
| **Colour (HSV)** | changes hue a little, saturation up to ±70%, brightness up to ±40% | default |
| **Rotation** | turns the photo | **0°** (off, as by default) |
| **Horizontal flip** | mirrors left to right, half the time by default | **off** ([`fliplr=0.0`, line 28](../../src/bestbefore/detector.py#L28)) |

```
 mosaic: 4 photos, each shrunk, in one training image
 ┌───────────┬───────────┐
 │ photo A   │ photo B   │   more objects per image, more of them small,
 │  EXP ▭    │      ▭    │   and objects cut off at the edges: all good
 ├───────────┼───────────┤   practice for a detector
 │ photo C   │ photo D   │
 │   ▭       │  ▭  ▭     │
 └───────────┴───────────┘
```

**Why flipping is off.** For cars or dogs a mirror image is realistic: a
car facing left is still a car. For text it isn't:

```
original:  15/08/2027
mirrored:  7202\80\51     never printed on any pack
```

Training on mirrored dates spends the model's effort on shapes that never
occur, and can blur what a real `2` or `7` looks like.

**Why rotation stays off.** Sideways dates do occur in the store photos.
But M2's question is "what do sideways synthetic dates add?", and that's
only measurable if M1 didn't already rotate everything. (Plain rotation
as a cheap rival is under Later in the plan.)

**Mosaic switches off at the end**
([`close_mosaic`](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/engine/trainer.py#L507-L510)),
so the last 10 epochs see whole photos like the real ones. You can see
it in the `n640` log: the training box loss drops suddenly at epoch 91,
the first epoch without mosaic, because whole photos are easier.

| Epoch | 88 | 89 | 90 | **91** | 92 |
|---|---:|---:|---:|---:|---:|
| box loss | 0.59 | 0.591 | 0.583 | **0.537** | 0.529 |

**Augmentation is only for training.** Validation, test and the store
photos are scored exactly as they are.

### 2.9 ○ GPU basics: memory, and waiting for photos

A **GPU** has thousands of small cores that do the same arithmetic on
many numbers at once, which is exactly what convolutions are. Two limits
matter:

1. **GPU memory limits the batch size.** The photos, every layer's
   feature maps (kept for the backward pass) and the gradients must all
   fit. From the log, on a 94 GB H100:

   | Run | GPU memory used | Batches per second |
   |---|---:|---:|
   | `n640` | 2.9 GB | 22.1 |
   | `s640` | 5.1 GB | 22.6 |
   | `n1280` | 12.5 GB | 13.5 |
   | `s1280` | 21.1 GB | 11.6 |

   Memory was never the limit: batch 16 used at most a quarter of it.
2. **The GPU can only work as fast as photos arrive.** Before each batch,
   CPU workers read 16 photos from disk, decode the JPEGs, build mosaics
   and resize. If that's slower than the GPU, the GPU waits. Look at the
   table: `s640` has 3.6× the parameters of `n640` and trained **just as
   fast**. If the GPU were the slow part, `s640` would be clearly slower.
   So the slow step, the **bottleneck**, was getting photos ready. The
   log even warns about the disk:

   ```
   WARNING ⚠️ train: Slow image access detected (ping: 19.5±12.6 ms, read: 17.7±3.8 MB/s ...)
   ```

   Our photos live on the cluster's shared network filesystem, not on a
   disk inside the GPU node. Caching photos in memory (`cache=True`) is
   the fix to try, under Later in the plan.

○ **Half precision (AMP).** The log's `AMP: checks passed` means training
did most arithmetic with 16-bit numbers instead of 32-bit: about twice as
fast on a GPU, very slightly less exact. That's why one validation date
got confidence 0.7226 on the laptop's CPU and just over 0.728 on the GPU
(§6, D2). `yolo26n.pt` is only fetched for this check.

## 3. Object detection: from features to boxes

This is the core of M1. §1 ended with 8,400 grid cells, each with a
column of features. This section turns them into boxes, trains them, and
scores them.

### 3.1 ★ What YOLO predicts at each grid cell

At every one of the 8,400 cells, the head outputs:

- **4 box numbers**: the distances from the cell's centre to the box's
  **l**eft, **t**op, **r**ight and **b**ottom edges, in cells;
- **4 class scores**, one per class, each turned into a probability from
  0 to 1 by a **sigmoid**.

```
 one cell of the 80 × 80 grid, on a date
                 t
          ┌──────┼──────────────┐
          │      │              │
        l ◄──────●──────────────► r        box = (cx − l, cy − t, cx + r, cy + b)
          │      │              │
          └──────┼──────────────┘           scores: date 0.86, due 0.01,
                 b                                   prod 0.00, code 0.02
```

4 + 4 = the **8** in the `(1, 8, 8400)` shape from §1.2. The class
scores are independent yes/no answers (that's why the loss is *binary*
cross-entropy), and the box's **confidence** is its highest class score.

This style is called **anchor-free**: the cell predicts the box directly
from its own position. (Older YOLOs started from preset box shapes,
"anchors", and adjusted them.)

**In Ultralytics' code**,
[the `Detect` head](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/nn/modules/head.py#L121-L139)
has two small branches per grid: `cv2` for the box and `cv3` for the
classes (the branch whose last layer was re-learned in §2.6).

○ **DFL.** `cv2` actually outputs 4 × 16 numbers, not 4. Instead of one
guess per edge, it gives a probability over 16 possible distances
(0 to 15 cells), and the edge is the average of that spread. This lets the
model say "the edge is between 3 and 4 cells away, nearer 4". The
matching part of the loss is the `dfl_loss` (*distribution focal
loss*) in the log.

### 3.2 ○ Which cells learn which box

8,400 cells, and a photo has maybe 3 labelled boxes. Which cells should
learn to predict which box, and which should learn "nothing here"?

YOLO11 decides afresh for every photo, every time, with a **task-aligned
assigner**
([`TaskAlignedAssigner`](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/utils/tal.py#L14)):

1. For each labelled box, look at the cells whose centre is inside it.
2. Score each by how good its current prediction already is: a mix of
   its class score and its box's IoU with the label.
3. The best **10** become **positives** for that box: they learn its
   position and class. Every other cell is a **negative**: it learns to
   give all 4 classes a score near 0.

So nearly all 8,400 cells are negatives in every photo. Most of training
is the model learning that most of a photo is not a date.

### 3.3 ★ The detection loss

The loss in the log has three parts
([`v8DetectionLoss`](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/utils/loss.py#L347-L381)):

```
loss = 7.5 × box_loss  +  0.5 × cls_loss  +  1.5 × dfl_loss
```

| Part | Asks | How | Code |
|---|---|---|---|
| **box_loss** | is each positive's box in the right place? | `1 − CIoU` with its label | [lines 134–135](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/utils/loss.py#L134-L135) |
| **cls_loss** | did every cell give the right class scores? | BCE over all 8,400 × 4 scores | [line 454](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/utils/loss.py#L454) |
| **dfl_loss** | are the edge distributions sharp and right? | DFL (§3.1) | [lines 138–141](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/utils/loss.py#L138-L141) |

The weights 7.5, 0.5 and 1.5 are Ultralytics' defaults
([`box`, `cls`, `dfl`](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/cfg/default.yaml#L103-L106),
applied at
[lines 469–471](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/utils/loss.py#L469-L471)).
They balance three numbers of very different sizes.

**CIoU** (*complete IoU*) is IoU (M0 §2.3) plus two small penalties: one
for the distance between the two boxes' centres and one for different
shapes. Plain IoU has a weakness as a loss: two boxes that don't touch
have IoU 0 whether they're 1 px or 300 px apart, so it can't say which
way to move. The centre-distance term can.

**Our real numbers** (`n640`, from the log; the printed values already
include the weights):

| Epoch | box_loss | cls_loss | dfl_loss |
|---:|---:|---:|---:|
| 1 | 1.336 | 2.008 | 1.151 |
| 10 | 0.885 | 0.711 | 0.943 |
| 50 | 0.675 | 0.474 | 0.868 |
| 100 | 0.507 | 0.311 | 0.818 |

All three fall: boxes get tighter, class scores get right. The
`cls_loss` falls fastest at the start (by two thirds in 10 epochs). One
reason: the class layer begins random (§2.6), so it has the most to
learn. A box_loss of 0.507 means the
average `1 − CIoU` is about 0.507 ÷ 7.5 ≈ 0.07, so on the training
photos the positive cells' boxes overlap their labels by roughly 0.93.

**A training loss is not a score.** These are measured on the augmented
*training* photos. Whether the model is any good is measured on
validation (§4.2).

### 3.4 ★ From 8,400 guesses to a few boxes: confidence, NMS, threshold

Each photo produces 8,400 candidate boxes. Three filters cut them down:

```
 8,400 candidates
   │  1. drop boxes with confidence < 0.001      (PREDICT_CONF, detector.py line 31)
   ▼
 a few hundred, many of them near-copies of each other
   │  2. NMS: of boxes that overlap with IoU > 0.7, keep only the most confident
   ▼
 a handful (at most 300)                          ← what detector.predict() returns
   │  3. our threshold: keep confidence ≥ 0.728   (applied when scoring, §3.5)
   ▼
 the boxes the M1 detector "reports"
```

**Why the near-copies.** Neighbouring cells all see the same date, and
several of them were trained as positives for it (§3.2). So they all
predict nearly the same box.

**NMS** (*non-maximum suppression*) cleans that up:

1. Sort the boxes by confidence, highest first.
2. Keep the top one.
3. Delete every remaining box whose IoU with a kept box is above 0.7.
4. Move to the next box that's still there, and repeat.

Ultralytics' NMS is **per class** by default: a `date` box never deletes
a `due` box, however much they overlap. It does this with a trick: it
shifts each class's boxes far apart before comparing
([`boxes = x[:, :4] + c`](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/utils/nms.py#L146-L159)).

**Why our two thresholds differ.**
[`predict()` keeps everything above 0.001](../../src/bestbefore/detector.py#L84-L98),
not above the real threshold. That way one prediction run can be scored
at **any** threshold afterwards (§3.5), and the threshold is chosen in
one place, by one rule, on validation.

([`auto=same_shapes and self.args.rect`](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/engine/predictor.py#L234-L243),

  single shape. It was caught while writing up, applied

  identically, and D3 re-scored. The expiry results didn't change (18,
  22 and 25 of 81), but only the second run could be trusted. **A risk
  written in the guide but not in the plan is a risk nobody checks.**

### 3.5 ★ Matching boxes to labels: our evaluator

To score, each reported box must be paired with a labelled date, or
counted as a false box. The rules, in
[`match_photo()`, lines 46–66](../../src/bestbefore/detection_eval.py#L46-L66):

1. Only `date` predictions and labelled dates take part
   ([`evaluate()`, lines 88–89](../../src/bestbefore/detection_eval.py#L88-L89)).
2. Predictions go **most confident first**
   ([line 53](../../src/bestbefore/detection_eval.py#L53)).
3. Each takes the **still unmatched** label it overlaps most, if that IoU
   is at least 0.5
   ([lines 56–64](../../src/bestbefore/detection_eval.py#L56-L64)).
4. A label can be taken only once, so one big box over two dates counts
   once, and a duplicate box counts as false
   ([tests, lines 49–63](../../tests/test_detection_eval.py#L49-L63)).

**Why our own evaluator**, when Ultralytics computes mAP: the YOLO labels
don't record which date is the **expiry**, so Ultralytics can't say
"637 of 665 expiry dates found". Ours works from `Sample`s, which do,
and will score the store photos the same way, by failure tag.

**The trick that makes thresholds cheap.** Whether a prediction matches
depends only on the predictions more confident than it. So we match
**once**, with every box down to 0.001, and record each label's matching
confidence. Then for **any** threshold `t`:

```
found   = labelled dates whose matching confidence ≥ t
kept    = predictions with confidence ≥ t
correct = kept predictions that matched
```

That's the whole of
[`summary()`, lines 114–116](../../src/bestbefore/detection_eval.py#L114-L116):
counting, with no re-matching.

**Cross-check.** Two independent tools should agree.
[`ultralytics_recall_at()`](../../src/bestbefore/detector.py#L146-L154)
reads Ultralytics' own recall at our threshold, and the experiment tables
mark `ok` when the two are within 0.02. They agreed on every run.

### 3.6 ★ Precision, recall and F1 at a threshold

- **Recall**: of the real dates, how many were found? `found ÷ dates`.
- **Precision**: of the boxes kept, how many were real dates?
  `correct ÷ kept`.
- **F1**: one number combining the two,
  `2 × precision × recall ÷ (precision + recall)`. It's high only when
  **both** are high.

The threshold slides between them: lower finds more dates and keeps
more junk; higher is cleaner and misses more.

**The real trade-off for the M1 detector** on the 165 validation photos
(187 dates), computed on the laptop:

| Threshold | Dates found | Recall | Boxes kept | Precision | False boxes / photo |
|---:|---:|---:|---:|---:|---:|
| 0.10 | 187 | 1.000 | 207 | 0.903 | 0.12 |
| 0.25 | 187 | 1.000 | 201 | 0.930 | 0.08 |
| 0.50 | 186 | 0.995 | 197 | 0.944 | 0.07 |
| 0.70 | 185 | 0.989 | 191 | 0.969 | 0.04 |
| **0.728** | **184** | 0.984 | 189 | 0.974 | 0.03 |
| 0.80 | 179 | 0.957 | 183 | 0.978 | 0.02 |
| 0.90 | 25 | 0.134 | 25 | 1.000 | 0.00 |

Notice:

- Down to 0.25, **every** date is found, for about 1 false box in 12
  photos.
- The cliff at 0.9: this model almost never goes above 0.9 at all. Its
  confidences are not "probabilities you can trust as stated"; they're
  scores, and only their order is reliable. That's why a threshold must
  be **chosen on data**, not guessed.
- On the cluster's GPU the 0.728 row is 185, not 184: the one date at
  0.7226 (§2.9, AMP).

**The F1-best threshold.**
[`best_threshold()`, lines 131–149](../../src/bestbefore/detection_eval.py#L131-L149)
sorts the predictions by confidence, and for each possible cut computes
precision, recall and F1 with running totals (`np.cumsum`), then takes
the best. Only the predictions' own confidences need trying: between two
of them, nothing changes. On the GPU this gave 0.728, the M1 threshold.

### 3.7 ★ mAP@0.5: one number for every threshold at once

Precision and recall depend on the threshold. **AP** (*average
precision*) scores the detector at all thresholds together:

1. Slide the threshold from high to low. At each step, write down recall
   and precision. Plotted, that's the **precision-recall curve**.
2. **AP** is the area under it. 1.0 means every date found before any
   false box, at every threshold.
3. **mAP** is the mean of AP over the classes. We report the `date` one.
4. **@0.5** means "found" is IoU ≥ 0.5.

```
 precision
 1.0 ┤██████████████████████████▄
     │██████████████████████████ █
     │██████ area = AP ██████████ █▄
 0.5 ┤██████████████████████████ ███
     │██████████████████████████ ███
     └──────────────────────────┬───┬─► recall
     0                        0.95  1.0
```

**mAP@0.5:0.95** repeats this at IoU 0.5, 0.55, …, 0.95 and averages, so
it rewards boxes that hug the date tightly. It's the column where the
bigger C1 settings did better (0.895 → 0.922): **tighter boxes, not more
dates found**. We need "found", so mAP@0.5 decides.

**Our per-class APs** (validation, laptop):

| `date` | `due` | `prod` | `code` |
|---:|---:|---:|---:|
| 0.991 | 0.887 | 0.912 | 0.778 |

The three marks score lower than dates, but the number of examples
alone doesn't explain the order: `prod` has the fewest training boxes
(100, against 895 for `due` and 541 for `code`) and still beats both.
How varied and how small a class's boxes are matters too. We train the
marks for M3's sake (decision 2) and judge only `date`.

**mAP doesn't depend on the threshold; recall does.** D2 found this the
hard way: three seeds with the same test mAP (0.993) found 637, 651 and
650 expiry dates, because each chose its own threshold on validation
(§6).

> compare with Ultralytics' 0.991.

## 4. ML method: how results are judged

### 4.1 ★ Train, validation, test: decide on validation, test once

The idea is in [m0 §3.1](m0.md#31--train-validation-and-test). Here is
everything M1 decided, and where:

| Decision | Made on |
|---|---|
| which epoch's weights become `best.pt` | validation, every epoch (§4.2) |
| model size and input size (C1) | validation |
| synthetic data or not (C2) | validation |
| the confidence threshold, 0.728 | validation |
| which seed's model is "the" M1 detector | **in advance**: seed 0, before any run |
| | |
| how good is it? | **test**, once (D2) |

Every one of those choices looked at validation scores, so the
validation numbers are a little flattering. The test score, made once
after every choice was frozen, is the honest one.

**The code enforces "once".**
[`eval_detector.py`, lines 41–43](../../scripts/eval_detector.py#L41-L43)
refuses to score a run on the test split a second time unless you pass
`--again` on purpose, and
[line 56](../../scripts/eval_detector.py#L56) always uses the threshold
from the run's validation file, never a new one.

### 4.2 ★ Overfitting, underfitting and early stopping

- **Underfitting**: the model hasn't learned enough yet. Training loss
  and validation score are both poor. Every run starts here (epoch 1 of
  `n640`: validation mAP@0.5 over the 4 classes 0.31).
- **Overfitting**: the model starts **memorising** the training photos
  instead of learning what a date looks like in general. Training loss
  keeps falling, but the validation score stops rising, or falls. Like a
  student who memorises past papers word for word and is lost on new
  questions.

**Early stopping** watches the validation score after every epoch, keeps
the best epoch's weights as `best.pt`, and stops if there has been no new
best for `patience` epochs (ours: 30,
[`detector.py`, line 26](../../src/bestbefore/detector.py#L26);
the check is
[`EarlyStopping`](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/utils/torch_utils.py#L1130-L1148)).

**It happened in `n1280`.** From the log:

| Epoch | Training box loss | Validation mAP@0.5:0.95 (4 classes) |
|---:|---:|---:|
| 30 | 0.607 | 0.765 |
| 66 | 0.519 | **0.802** ← best |
| 80 | 0.491 | 0.795 |
| 96 | 0.418 | 0.798 |

```
EarlyStopping: Training stopped early as no improvement observed in last 30 epochs.
Best results observed at epoch 66, best model saved as best.pt.
```

After epoch 66 the training loss fell another 20% while validation went
nowhere: everything learned after 66 fitted the training photos only.
`s1280` stopped the same way (best at epoch 57).

**`n640` never stopped.** It kept finding small new bests up to epoch 98
(mAP@0.5:0.95 0.704 at epoch 80, 0.709 at 98), so it may still have been
improving. "Train longer" is under Later in the plan.

○ **What "best" means to Ultralytics.** Its
[`fitness`](https://github.com/ultralytics/ultralytics/blob/v8.4.177/ultralytics/utils/metrics.py#L1017-L1020)
is mAP@0.5:0.95 averaged over all 4 classes, not our mAP@0.5 for dates.
So `best.pt` is the epoch with the tightest boxes overall. That's fine
for us, since the two rise together, but it's worth knowing that the tool
and the project optimise slightly different numbers.

○ The training photos are many and varied (12,795, augmented every
time), so overfitting came late. The real-only run, with 937 photos,
is where it would bite first.

### 4.3 ★ Data leakage

**Leakage** is any way test information reaches the model or your
choices; the score then lies upwards, silently
([m0 §3.2](m0.md#32--data-leakage)). How M1 guards against it:

| Risk | Guard |
|---|---|
| choosing the threshold on test or store photos | chosen on validation by a fixed rule (F1), then frozen |
| choosing the input size from store-photo date sizes | decision 8: settings come from ExpDate validation only, even though the store sizes were tempting |
| bending a decision rule after seeing results | the rules were written in the plan **before** any run, and are code ([`m1.py`, lines 21–37](../../src/bestbefore/m1.py#L21-L37)) the chain applies on its own |
| re-scoring test until it looks good | the evaluator refuses a second test run (§4.1) |
| the same photo in train and validation | checked: one validation photo, `img_00277.jpg`, is reused 14 times by the synthetic set; at most 1 of 165, so no choice changed ([experiment](../../experiments/expdate-near-duplicates/README.md)) |
| store photos reaching training | they never leave the laptop, so they can't even reach the cluster |

The D2 threshold finding (§4.7) is the hardest case: we **knew** a
better threshold after looking at test, and didn't use it. That's the
discipline that makes the 637/665 believable.

### 4.4 ★ Domain shift: why 0.993 isn't the headline

M1's mAP@0.5 of 0.993 is on ExpDate test: the **same kind** of photos it
trained on. It shows the detector learned ExpDate. It doesn't show it
works in your stores ([m0 §3.3](m0.md#33--domain-shift)).

| | ExpDate (trained and tested) | Store photos (D3) |
|---|---|---|
| where | packs photographed in shops, many Korean | staff phones in Indian pet stores |
| sideways dates | almost none | 15 of 81 expiry dates |
| dates with the month as a word | about 6% | 26 of the 66 others |
| median date height at 640 px | 15.5 px | 11.0 px |
| **expiry dates found** | **97%** (637 of 665) | **27%** (mean of 3 seeds) |

Two signs the ExpDate score is too easy to separate models:

- **Ceiling effect.** In C1 all four settings found 185 to 187 of 187
  validation dates. When everyone scores 99%, the exam can't tell them
  apart. It shows "on these photos size doesn't matter", not "size never
  matters".
- **Synthetic vs real is a small domain shift too.** Synthetic dates are
  bigger (median 27 px vs 16 px tall at 640). C2: adding 11,858 of them
  bought about 1 point (185 vs 179 dates found).

D3 measured the real gap: from 97% to 27%. By tag, sideways and small
print are 0 of 15 each, clean 23%, and dot-matrix, the kind ExpDate is
full of, 73%. Splitting the misses
([`experiments/m1-store-misses`](../../experiments/m1-store-misses/README.md))
found two causes besides sideways dates: **dates with the month as a
word are almost never found** (3%), and **numeric dates are found by
size** (87% when large, 12% when small). A detector learns what its
training dates look like, and no more. M2 then tries to close the gap
with synthetic dates that look like the store packs, and it will be
judged on the store photos, not on ExpDate.

### 4.5 ○ Seeds and run-to-run noise

Training has randomness: the new head's starting weights, the order of
photos, every augmentation. The **seed** fixes all of it
([`seed=seed`](../../src/bestbefore/detector.py#L70) and
[`deterministic=True`](../../src/bestbefore/detector.py#L29)), so a run
can be repeated. A different seed gives a slightly different model.

**How big is the wobble?** D1 trained `n640` with seeds 0, 1 and 2:
validation mAP@0.5 0.991, 0.991, 0.994. A range of 0.003.

**How small a difference can 187 dates show?** One date is 1 ÷ 187 =
**0.53 points** of recall. And if the true recall is 99%, the counting
noise alone (the binomial standard error, `√(p(1 − p) / n)`) is about
**0.7 points**. So a 1-point difference is within what luck alone
produces. That's where the C1 and C2 rule "differences under 1 point are
noise" comes from
([`NOISE = 0.01`](../../src/bestbefore/m1.py#L21)).

**Why seed 0 was declared the M1 detector in advance.** If you train 3
and keep the best on test, you've chosen by the test score (§4.1).

### 4.6 ○ Baselines and ablations: change one thing at a time

An **ablation** removes or changes one thing and measures the
difference. C1 is a grid of two (size, input). C2 is an ablation of the
synthetic photos: same everything, with and without.

**A finding (2026-10-20): C2 changed two things, not one.** The C2 README
says the two runs are "identical except" the training photos. But
`optimizer=auto` picks by the number of steps (§2.4), and the real-only
run has about 14× fewer photos, so it got a **different optimiser**:

| Run | Training photos | Optimiser chosen | Learning rate |
|---|---:|---|---:|
| `n640` | 12,795 | MuSGD | 0.01 |
| `n640-real` | 937 | AdamW | 0.00125 |

So the 1-point gain can't all be credited to the synthetic photos; part
could be the optimiser. **The decision doesn't change**: the rule keeps
synthetic data unless real-only wins by more than 1 point, and real-only
was worse. But the claim "synthetic data helps a little" is weaker than
it looked. The fix for M2's ablation is cheap: set `optimizer` and `lr0`
explicitly in `SETTINGS`, so the tool can't change them behind your
back.

The lesson: **a default that adapts to the data is a hidden variable.**
Read the log of every run in an ablation, not just its score.

**Baselines.** M1 has no detection baseline yet (one is under Later:
RapidOCR's own text boxes). The reading baselines A and B come in M0
Part C, and M1 is judged only on finding dates, because RapidOCR reads
crops worse than whole photos (CLAUDE.md, lessons).

### 4.7 ★ Choosing a threshold by the cost of errors

F1 treats a missed date and a false box as **equally bad**. Is that true
for us? It depends on the stage:

| Stage | Error | What it costs |
|---|---|---|
| **detector** (M1) | a missed date | the reader never sees it: a guaranteed "none" for that pack |
| | a false box | the reader looks at a bit of packaging, reads no date, moves on |
| **reader** (M3) | no date read ("none") | staff type it in: seconds |
| | a wrong date read | `08/2027` as `08/2021`: a good batch marked expired, unnoticed |

So for the **detector**, a miss is worse than a false box, and the
threshold should lean towards recall. For the **reader**, a wrong date is
worse than none, so it should lean towards saying nothing when unsure.
The same idea, "price the errors, then choose", gives opposite leanings
at the two stages.

**What D2 showed.** The detector put a box on **all 665** test expiry
dates at some confidence. The 28 it missed were all there, under 0.728.
The dot-matrix expiry on `img_00003.jpg` (§3.4) is the same thing on
validation. F1 was the wrong rule for this stage.

**A better rule**, under Later in the plan: the **highest threshold that
still keeps validation recall at 99% or more**. Exercise 5 works it out.
It's only allowed to be used for the next test (M2's detector), decided
on validation before that test, never applied back to D2.

## 5. Training on a shared cluster

All ○: practical knowledge, worth a sentence in an interview.

**Login node vs compute nodes.**

```
  laptop ──ssh──►  LOGIN NODE                ──Slurm──►  COMPUTE NODES (cn5, cn6)
                   has internet                          2 × H100 each
                   light work only:                      no internet
                   downloads, setup, sbatch              Slurm runs your job here
```

- The login node is shared: never train on it.
- Compute nodes have **no internet**, so everything a job needs is
  fetched on the login node first:
  [`fetch_pretrained.py`](../../scripts/fetch_pretrained.py) gets the
  weights and Ultralytics' plot font, and the chain sets
  [`YOLO_OFFLINE=1`](../../slurm/m1_chain.sh#L9) so Ultralytics doesn't
  even try.
- **Modules** switch software on per shell: `module load Python/3.11.11`
  is needed in every job, because the venv's Python links to the
  module's `libpython3.11.so`.
- **The driver decides the PyTorch.** PyTorch build → CUDA version → GPU
  driver must agree; that's why torch is the `cu128` build.

**Slurm, the queue.**

| Word | Meaning |
|---|---|
| `sbatch script` | submit a job; it runs in the background when resources are free |
| `squeue -u $USER` | your jobs: waiting (`PD`) or running (`R`) |
| `scancel <id>` | cancel a job |
| partition | a group of machines with rules; ours is `gpu` |
| `--gres=gpu:1` | "one GPU, please" |
| QOS limit | 2 jobs at a time for our account |

The job script is a shell script with `#SBATCH` lines saying what it
needs: [`m1_holder.sbatch`, lines 12–18](../../slurm/m1_holder.sbatch#L12-L18).

**Holding a place in the queue.** The queue is first come, first served
(`sprio`: every job has priority 1). Slurm reads a job's files when the
job **starts**, so we submitted a placeholder (job 72789) early, wrote
the chain while it waited, and it ran whatever was there by then. If the
chain wasn't ready, it would
[exit at once](../../slurm/m1_holder.sbatch#L23-L26) rather than hold an
idle GPU.

**One job, many runs.** [`m1_chain.py`](../../scripts/m1_chain.py) ran
everything back to back in that one job: the smoke test, C1's four runs,
the C1 decision, C2, the C2 decision, the two extra seeds. Two habits
made that safe:

- **Resumable**: a run whose `val.json` exists is
  [skipped](../../scripts/m1_chain.py#L38-L40), so a resubmit carries on
  where a cut-off job stopped.
- **Decisions as code**: the chain applies the rules from `m1.py`
  ([lines 62–79](../../scripts/m1_chain.py#L62-L79)) and writes them to
  `m1-decisions.json`. Nobody had to choose by hand at 3 am, and nobody
  could bend a rule after seeing the numbers.

**Run records.** Every run starts with
[`start_run()`](../../src/bestbefore/runs.py#L41-L58): command, git
commit, seed, settings, library versions, GPU name. Any number in
`results/` can be traced back to exactly what made it.

**Code and results flow one way each.** Code: laptop → GitHub →
`git pull` on the cluster. Results: cluster → `rsync` → laptop. All
commits happen on the laptop. Weights (5.5 MB each) come to the laptop
only when needed, and the store photos never go the other way.

## 6. What each slice taught us

Short lessons, in the order they happened. The numbers are in the plan
and the experiment READMEs.

**A1, setup (14 Oct).**
- `python` was "command not found": the cluster's module provides only
  `python3` (inside the venv both work).
- `pip install torch` picked a CUDA 13 build that the cluster's driver
  can't run. It would have installed fine and then reported "no GPU" in
  every job. We checked the driver first and installed the CUDA 12.8
  build. On a shared cluster you can't upgrade the driver, so you pick
  the PyTorch that fits it.

**A2, data on two machines.**
- The downloads were **checked, not trusted**: their SHA-256
  fingerprints matched the laptop's, and so did the four image lists
  after conversion. Seed 0 made both machines pick the same 165
  validation photos.

**A3 and B1, smoke tests and the training code.**
- A smoke test checks the **plumbing, not the quality**: 1 epoch on 19
  photos in 26 seconds on the laptop, scores about 0, but every piece
  connected.
- Ultralytics quietly downloads things (weights, a check model, a font).
  On a compute node each would fail, so they're fetched ahead.
- 37 tests before trusting the evaluator. One test was itself wrong (it
  expected a match at IoU *exactly* 0.5, which rounding put at
  0.4999…). Fixing the test, not the code, was right.
- `m1_chain.py --dry-run` printed the whole plan on the cluster before
  the GPU job reached it.

**C1, C2 and D1, the overnight job (15–16 Oct).** 8 trainings in 7 h 42
min on one H100.
- **Ceiling effect**: all four C1 settings found 185–187 of 187 dates,
  so the rule took the cheapest, `n640`.
- **Bigger settings gave tighter boxes, not more dates** (mAP@0.5:0.95
  0.895 → 0.922).
- **Synthetic data helped a little** (185 vs 179 dates found), with the
  optimiser caveat of §4.6.
- **Three seeds, nearly the same** (0.991, 0.991, 0.994), so the
  one-seed comparisons weren't luck.
- **Estimates are guesses until measured**: about a day estimated,
  under 8 hours taken; and `s640` trained as fast as `n640`, which
  pointed at data loading, not the GPU (§2.9).

**D2, the test split, once (16 Oct).**
- **Check the measuring tool first**: validation re-scored on the
  laptop's CPU matched the GPU except one date (0.7226 vs just over
  0.728, half precision).
- **A model can see a date and still miss it**: boxes on all 665 test
  expiry dates; the 28 misses were under the threshold.
- **Same mAP, different recall**: the seeds' thresholds differed (0.728
  vs about 0.665), and seed 0 found 14 fewer expiry dates.
- **Knowing a better rule after the test doesn't let you use it there.**

**D3, the store photos, once (21 Oct).**
- **97% on ExpDate became 27% in the stores** (mean of 3 seeds). This
  is the number M1 was really for (§4.4).
- **Check the harness before believing a bad number**: dot-matrix at 73%
  ruled out a coordinate bug, and IoU 0.3 adding almost nothing ruled
  out a box-convention mismatch.
- **"Boxed at any confidence" splits the misses**: 56% of expiry dates
  get some box, but most fall under 0.728. Small print is mostly not
  seen at all (36% boxed); clean print is mostly seen but doubted (68%).
- **Group the failures by a cause you can measure**: format and print
  size explained most of the clean misses, which the failure tag alone
  didn't.
- **A first analysis can be wrong in a silly way**: `DD/MM/YYYY` holds
  letters, so "has letters" put every format in "month as a word".
  Looking at the group sizes (66 and 0) caught it.

**D4, the report (21 Oct).**
- **The report is rebuilt from the run records by a script**, never
  typed: [`m1_report.py`](../../scripts/m1_report.py) reads each run's
  `val.json`, `real-test.json` and `store.json`. A number in it can't
  drift from the runs, and anyone can regenerate it.
- **A record should say whether the code was committed.** The first D3
  record named a commit that didn't contain the padding fix it ran with.
  Scores now record `git_dirty` too, and the report shows it.
- **Compare like with like, or not at all.** The ExpDate paper reports
  97.74% for *reading* expiry dates. That's M3's comparison, not a
  detector's, so the report says "no comparable number" instead of
  setting the two side by side.

**Writing this guide (20 Oct).**
- **`optimizer=auto` made C2 a two-variable comparison** (§4.6).
- **Confidence depends on padding, which depends on the batch** (§3.4).
  Harmless for D1 and D2, to fix before D3.
- Reading the log of every run turned up both. Scores alone didn't.

from bestbefore.detection_eval import iou

def nms(boxes, scores, iou_max=0.7):
    order = sorted(range(len(boxes)), key=lambda i: -scores[i])
    keep = []
    for i in order:
        if all(iou(boxes[i], boxes[k]) <= iou_max for k in keep):
            keep.append(i)
    return keep

<summary>Answer to 4</summary>

```python
import numpy as np
order = np.argsort(-np.array(m.pred_conf), kind="stable")
tp = np.array(m.pred_tp)[order]
correct = np.cumsum(tp)
recall = correct / len(m.truth_conf)
precision = correct / np.arange(1, len(tp) + 1)

# make precision never rise as recall grows, then take the area
mrec = np.r_[0, recall, 1]
mpre = np.flip(np.maximum.accumulate(np.flip(np.r_[1, precision, 0])))
x = np.linspace(0, 1, 101)
print(np.trapezoid(np.interp(x, mrec, mpre), x))      # 0.9919
```

0.992 against Ultralytics' 0.991: the same idea, with small differences
in how the two tools prepare photos and match boxes. The 101 points are
the COCO convention, which Ultralytics follows. Adding up
`precision[tp].sum() / len(m.truth_conf)` instead (area as exact
steps) gives 0.997.
</details>

<details>
<summary>2. Why does YOLO predict on three grids instead of one?</summary>

Small objects need small cells (the 80 × 80 grid, 8 px each); big objects
need cells that see a lot of the photo (20 × 20). Three grids cover both.
</details>

<details>
<summary>3. Why does a network need an activation function at all?</summary>

Without one, any stack of layers is still a single weighted sum, a
straight-line model. The activation bends it, so stacked layers can learn
complicated rules.
</details>

<details>
<summary>4. The loss went up after one step. Name a likely cause and a fix.</summary>

The learning rate is too high, so the step overshot the valley. Lower it,
or warm it up from 0.
</details>

<details>
<summary>5. With 12,795 photos, batch 16 and gradients added over 4 batches, how many weight updates in one epoch?</summary>

800 batches ÷ 4 = 200 updates.
</details>

<details>
<summary>6. "Transferred 493/499 items." What are the 6, and why weren't they transferred?</summary>

The last class layer at each of the 3 grids, weight and bias. COCO's has
80 outputs, ours 4, so the shapes don't fit; they start random.
</details>

<details>
<summary>7. What is NMS for, and why is ours per class?</summary>

Neighbouring cells predict near-copies of the same box; NMS keeps the
most confident and deletes copies with IoU over 0.7. Per class, so a
`date` box can't delete the overlapping `due` box next to it.
</details>

<details>
<summary>8. At some threshold the detector keeps 20 boxes, 15 of them real dates, out of 18 dates. Precision, recall, F1?</summary>

Precision 15/20 = 0.75. Recall 15/18 = 0.83. F1 = 2 × 0.75 × 0.83 ÷ 1.58
= 0.79.
</details>

<details>
<summary>9. Training loss keeps falling, validation mAP has been flat for 30 epochs. What's happening, and what does Ultralytics do?</summary>

The model is fitting the training photos without getting better on new
ones: overfitting. Early stopping ends training and keeps the best
epoch's weights as best.pt (as in n1280).
</details>

<details>
<summary>10. Three seeds have the same mAP but find different numbers of expiry dates. How?</summary>

mAP doesn't depend on the threshold; recall does. Each seed chose its own
threshold on validation, and the strictest one found fewer.
</details>

<details>
<summary>11. Why did C2 not test "synthetic data" alone?</summary>

optimizer=auto chose MuSGD for the 12,795-photo run and AdamW for the
937-photo run, so two things changed at once.
</details>

<details>
<summary>12. For the detector, is a missed date or a false box worse? For the reader?</summary>

Detector: a missed date, because it can never be read. Reader: a wrong
date, because nobody notices it.
</details>

<details>
<summary>13. Why must augmentation never be applied to validation or test photos?</summary>

Those photos measure how the model does on real photos as they are.
Changing them would measure something else, and differently each time.
</details>

<details>
<summary>14. On the store photos M1 finds 73% of dot-matrix expiry dates but only 23% of clean ones. How can clean print be harder?</summary>

The failure tag describes the print, but the detector's misses follow
what it was trained on. ExpDate is full of numeric dot-matrix dates, so
those look familiar: 19 of the 20 dot-matrix store expiries are numbers
only. But 16 of the 31 clean ones write the month as a word
(`December 2026`), and the detector finds 3% of month-word dates.
Grouping the misses by format (`experiments/m1-store-misses`) found
that; the tag alone didn't.
</details>

<details>
<summary>15. Could M1 now switch to n1280, since it finds small dates better?</summary>

Not inside M1. The input size was chosen on validation, and the store
photos only judge it; choosing by them would be tuning on the test set.
Whether 1280 px helps on the store photos is a question for M2, written
down before any n1280 store result exists.
</details>

## Glossary

| Word | Meaning |
|---|---|
| Activation function | the bend after a neuron's sum: ReLU `max(0, z)`; YOLO uses SiLU |
| AMP / half precision | doing most arithmetic in 16-bit numbers: faster on a GPU, very slightly less exact |
| Anchor-free | each grid cell predicts a box directly, as distances to its four edges |
| AP / mAP | area under the precision-recall curve / its mean over classes |
| Augmentation | training on randomly changed copies of photos |
| Backbone / neck / head | feature extractor / mixer of fine and coarse maps / box and class outputs |
| Backpropagation | working out every weight's gradient in one backward pass, by the chain rule |
| Batch | photos processed together in one forward and backward pass |
| Batch norm | rescales feature maps to a steady range, for stable training |
| BCE | binary cross-entropy: the loss for one yes/no probability, `−log(p)` for the right answer |
| Bottleneck | the slowest step, which sets the pace for the whole |
| Ceiling effect | a test so easy everyone scores near the top, so it can't tell them apart |
| CIoU | IoU plus penalties for centre distance and shape: YOLO's box loss |
| Confidence | the model's score for a box, 0 to 1; only the order is reliable |
| Convolution | sliding a small filter over an image, multiplying and adding at each position |
| DFL | predicting each box edge as a spread over 16 distances |
| Early stopping | stopping when validation hasn't improved for `patience` epochs |
| EMA | a smoothed copy of the weights, averaged over recent steps; what `best.pt` holds |
| Epoch | one pass over all the training photos |
| F1 | `2PR / (P + R)`: high only when precision and recall both are |
| Feature map | a filter's output: where in the image its pattern appears |
| Fine-tuning | continuing to train a pretrained model on your own data |
| GFLOP | a billion multiply-adds: a measure of computation |
| Gradient | how much the loss rises when one weight rises a little |
| Gradient accumulation | adding up several batches' gradients before one step |
| Gradient descent | step each weight against its gradient, by the learning rate |
| Iteration | one batch |
| Learning rate | the size of each gradient-descent step |
| Letterboxing | resizing without stretching, padding with grey |
| Loss | one number for how wrong the model is |
| Momentum | keeping some of the previous step's direction |
| Mosaic | 4 training photos stitched into one |
| Neuron | weighted sum of inputs, plus a bias, through an activation |
| NMS | keep the most confident of overlapping boxes, delete the rest |
| Optimiser | the recipe that turns gradients into steps (SGD, AdamW, MuSGD) |
| Overfitting / underfitting | memorising the training photos / not having learned enough yet |
| Parameters / weights | the numbers training adjusts; `yolo11n` has 2.6 million |
| Patience | epochs without a new best before early stopping |
| Positive / negative (cell) | a grid cell assigned to learn a box / to say "nothing here" |
| Precision / recall | share of kept boxes that are real / share of real dates found |
| Pretrained weights | a model already trained on a big general dataset (COCO) |
| Receptive field | the area of the photo a cell has, in effect, seen |
| Seed | the starting number for every "random" choice in training |
| Sigmoid | squashes any number into 0..1 |
| Stride | how far a filter jumps each step; stride 2 halves the size |
| Threshold | the confidence below which boxes are thrown away |
| Transfer learning | reusing what a model learned on one task for another |
| Warmup | raising the learning rate from 0 over the first epochs |
